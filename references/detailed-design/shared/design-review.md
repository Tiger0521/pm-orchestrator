# 设计审查与反谄媚

本文件定义详细设计阶段跨 Step 共用的设计自检机制和反谄媚与前提挑战原则。仅在执行设计动作、生成草案前读取。

**职责边界**：本文件只管审查机制与质量阻断原则。各 Step 的执行流程见对应 step 文件夹的 `workflow.md`；写作规范见 `design-writing.md`。

---

## 1. 设计审查机制

借鉴 office-hours 的 Spec Review Loop（对抗式审查），详细设计阶段在草案生成后、用户确认前，subagent 内部执行一轮设计自检。

**审查维度**：

| 审查维度 | 检查问题 |
| ---- | ---- |
| 完整性 | 所有 Story 是否都有归属页面？有没有遗漏的异常场景？ |
| 一致性 | 页面间的跳转关系是否与页面映射表一致？交互规则是否与 GWT 验收标准一致？ |
| 可实施性 | 开发能否根据原型和交互契约直接开工？有没有模糊地带？ |
| 复用性 | 跨页面的相同交互模式是否统一？组件是否标注复用？ |
| 边界覆盖 | 空状态、加载中、错误状态、权限不足、网络异常是否都有展示方案？ |

**自检规则**：任一维度不满足时，subagent 在返回草稿前自行修正，不在草稿中暴露审查过程。审查不通过的项目记录到 `tracking-log.md`，标注为待解决。

**Step 1 特有补充**：Step 1 的自检额外覆盖"三份产物一致"——业务流文档、页面映射文档与两张 HTML 图的页面名称、层级、动线必须一致，用户直接编辑某份文件后其余文件需同步。

## 2. 反谄媚与前提挑战

**核心原则**：不要为了推进流程而附和用户。对不确定结论保持显式标记，不把假设写成事实。

**阻断条件**：以下情况必须阻止落盘，返回 `needs-input` 或 `blocked`--

- 上游 Story 不清晰
- 关键交互规则缺失
- 用户确认缺失

**落盘前自检**：每步落盘前，通读全文逐字段快查--

| 自检项 | 检查内容 |
| --- | --- |
| Step 1（业务流/页面映射） | 是否覆盖所有 Story；页面名称两份文档一致；HTML 图与文档一致 |
| 原型 | 是否含交互说明和异常状态 |
| 交互契约 | 是否有状态机和兜底 |
| 规则摘要 | 是否引用而非重复展开 |
| Sprint | 是否标注依赖和风险 |

任一项不满足时，不得落盘，必须先修正。
