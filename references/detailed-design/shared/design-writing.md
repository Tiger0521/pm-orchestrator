# 详细设计文档写作规范

> 本文件定义详细设计阶段 Step 2-3 文档产出的写作规范（迭代规划由 sprint-planning 阶段复用），包括 GWT 交互文案、交互规则表、错误提示文案、规则摘要的格式要求，以及落盘前的自检清单。
>
> Step 1 两份文档（业务流、页面映射）的写作规范分别见 `../step1-功能架构与动线规划/business-flow-writing.md` 和 `../step1-功能架构与动线规划/page-mapping.md`。`instruction.md` 引用本文件作为设计时的写作标准；`checklist.md` 引用本文件作为质量校验的判断依据。本文件不包含各 Step 执行流程（见对应 step 文件夹的 `workflow.md`）。

## 1. GWT 交互文案写作规范

### 1.1 格式定义

GWT 是交互契约中异常兜底列的标准格式，借鉴需求拆解阶段的 GWT 验收标准，但从验收口径转为实现口径。

```
Given [前置状态]
When [触发动作]
Then [系统行为]
```

- **Given**：描述触发动作发生前用户或系统的具体前置状态。
- **When**：描述用户的具体触发动作或系统的具体触发事件。
- **Then**：描述系统的具体行为，包括弹出文案、状态流转、数据操作等。

### 1.2 好差对比

| | 写法 | 评价 |
| --- | --- | --- |
| 好 | Given 用户已填写表单但未提交 / When 用户点击浏览器关闭按钮 / Then 系统弹出确认弹窗"您有未保存的内容，确认离开？" | Given 指明具体前置状态（已填写但未提交），When 指明具体触发动作（点击关闭按钮），Then 指明具体系统行为和文案（弹出确认弹窗并带具体提示语） |
| 差 | Given 用户在页面上 / When 用户操作 / Then 系统提示 | Given 只说"在页面上"未说明关键状态，When 只说"用户操作"未指明具体动作，Then 只说"系统提示"未说明提示内容和方式 |
| 好 | Given 订单状态为"已发货" / When 用户点击"再次发货"按钮 / Then 系统拦截操作并提示"该订单已发货，无法重复发货" | Given 指明具体状态值（已发货），When 指明具体按钮（再次发货），Then 指明拦截行为和具体文案 |
| 差 | Given 订单有问题 / When 用户操作订单 / Then 系统报错 | Given 状态模糊（"有问题"无具体值），When 动作模糊（"操作订单"无具体操作），Then 行为模糊（"报错"无具体文案） |
| 好 | Given 网络已断开 / When 用户点击"提交"按钮 / Then 系统保留已填表单内容并提示"网络异常，请检查网络后重试" | Given 指明具体环境状态（网络断开），When 指明具体动作（点击提交），Then 指明保留行为和具体文案 |
| 差 | Given 网络不好 / When 用户提交 / Then 系统处理失败 | Given 状态不精确，When 动作不精确，Then 缺少用户可感知的具体反馈 |

### 1.3 写作规则

| 规则 | 要求 | 违反后果 |
| --- | --- | --- |
| Given 必须指定具体前置状态 | 写明用户当前处于什么状态、数据处于什么状态、系统处于什么状态，不能用"在页面上""已操作"等模糊表述 | GWT 无法指导开发和测试，质量门不通过 |
| When 必须指定具体触发动作 | 写明用户点击了哪个按钮、执行了什么操作、系统发生了什么事件，不能用"用户操作""用户提交"等无指向表述 | 异常兜底无法落地为具体交互逻辑 |
| Then 必须指定具体系统行为并含具体文案 | 写明系统拦截还是放行、弹出什么弹窗、提示什么文案、数据做什么操作，文案须用引号标注 | 开发无法确定实现方式和用户可见反馈 |

## 2. 交互规则表写作规范

### 2.1 格式定义

交互规则表是交互契约文档（contract-\*.md）的核心字段，采用四列表格格式：

| 触发动作 | 校验判断依据（前/后端） | 状态流转与反馈 | 异常兜底处理（GWT） |
| --- | --- | --- | --- |
| （具体用户动作） | （前端校验/后端校验） | （状态流转和反馈） | （GWT 格式的异常兜底） |

### 2.2 好差对比

| | 写法 | 评价 |
| --- | --- | --- |
| 好 | \| 提交表单 \| 前端正则 + 后端唯一性校验 \| When 不符合【BR-01】，Then 拦截并提示 \| 并发冲突展示全局报错弹窗并提供刷新 \| | 触发动作具体、校验分前后端、流转引用规则 ID、兜底有具体策略 |
| 差 | \| 提交 \| 校验 \| 拦截 \| 报错 \| | 触发动作不具体、校验未分前后端、流转未引用规则、兜底只有"报错"无策略 |
| 好 | \| 点击"删除" \| 前端二次确认 + 后端权限校验 \| When 权限不足【NFR-Auth-01】，Then 按钮置灰并提示"无操作权限" \| Given 用户无删除权限 / When 点击"删除"按钮 / Then 按钮置灰并提示"您无删除权限，请联系管理员" \| | 校验分前后端、流转引用权限规则 ID、兜底用完整 GWT 格式 |
| 差 | \| 删除操作 \| 有权限校验 \| 拦截 \| 给提示 \| | 校验未分前后端、流转无规则引用、兜底无 GWT 格式无具体文案 |

### 2.3 写作规则

| 规则 | 要求 | 违反后果 |
| --- | --- | --- |
| 触发动作必须具体 | 写明"提交表单""点击删除""切换 Tab"等具体用户动作，不用"提交""删除""操作"等无指向表述 | 交互规则无法对应具体交互元素 |
| 校验必须区分前/后端 | 写明"前端正则 + 后端唯一性校验""前端二次确认 + 后端权限校验"，区分前端和后端各自负责什么 | 开发无法判断校验逻辑放在哪一层 |
| 状态流转必须引用规则 ID | 流转条件引用业务规则编号（如【BR-01】）或权限编号（如【NFR-Auth-01】），不在表格中展开规则全文 | 规则引用关系断裂，与规则摘要文档不一致 |
| 异常兜底必须用 GWT 格式 | 兜底列写完整 GWT（Given 前置状态 / When 触发动作 / Then 系统行为），含具体提示文案 | 质量门不通过，`validate-paradigm.sh` 报警告 |

## 3. 错误提示文案写作规范

### 3.1 格式定义

错误提示是交互契约文档（contract-\*.md）的必备字段，采用两列表格格式：

| 错误场景 | 提示文案 |
| --- | --- |
| （具体错误场景描述） | （面向用户的一句话提示） |

### 3.2 好差对比

| | 错误场景 | 提示文案 | 评价 |
| --- | --- | --- | --- |
| 好 | 模型名称为空 | 请输入模型名称 | 场景具体，文案面向用户，含动作指引（"请输入"） |
| 差 | 输入错误 | 出错了 | 场景模糊，文案无指向，用户不知道该做什么 |
| 好 | 模型名称已存在 | 该模型名称已存在，请修改后重试 | 场景具体，文案说明问题并给修改指引 |
| 差 | 重复 | 操作失败 | 场景模糊，文案无指引 |
| 好 | 网络请求失败 | 网络异常，请稍后重试 | 场景具体，文案面向用户，含重试指引 |
| 差 | 网络问题 | 请重试 | 场景不够具体，文案缺少原因说明 |
| 好 | 权限不足 | 您无操作权限，请联系管理员 | 场景具体，文案说明问题并给联系方式指引 |
| 差 | 没权限 | 操作失败 | 场景模糊，文案无指引 |

### 3.3 写作规则

| 规则 | 要求 | 违反后果 |
| --- | --- | --- |
| 每个错误场景对应一句具体文案 | 一个错误场景只对应一句提示语，不合并多个场景到一条文案 | 用户无法区分不同错误原因 |
| 使用面向用户的语言 | 用"请输入""请修改""请联系管理员"等用户可理解的表述，不用"校验失败""接口返回 500"等技术术语 | 用户无法理解提示含义 |
| 尽可能包含动作指引 | 文案不仅说明问题，还指引用户下一步操作（"请输入""请修改后重试""请联系管理员"） | 用户看到提示后不知道该做什么 |
| 禁止使用泛词 | 不使用"出错了""操作失败""请重试""错误"等无指向的泛词作为唯一文案 | 质量门不通过，`validate-paradigm.sh` 报警告 |

## 4. 规则摘要写作规范

### 4.1 核心原则

规则摘要遵循"引用 + 摘要"原则，而非全文展开。宏观业务逻辑（规则/权限等）上提至全局知识库，交互说明中仅做规则引用，不在页面说明中重复展开全文。新生成的全局规则需沉淀至企业/项目级独立知识库，并在当前迭代的规则摘要中以列表形式汇总引用。

### 4.2 格式定义

规则摘要文档（rules-\*.md）中的业务规则、数据字典、权限控制、安全审计等字段均采用"编号 + 摘要 + 影响范围"的引用格式：

| 分类 | 字段结构 | 示例 |
| --- | --- | --- |
| 业务规则 | BR-XXX + 定义与约束摘要 + 影响范围/研发关注点 | BR-Promo-01：满减互斥规则，影响结算页价格计算逻辑 |
| 数据字典 | DD-XXX + 定义与约束摘要 + 影响范围 | DD-Order-Status：订单状态机，影响所有展示订单状态的列表页 |
| 权限控制 | NFR-Auth-XX + 定义与约束摘要 + 影响范围 | NFR-Auth-01：RBAC + 行级数据权限，影响所有列表查询接口 |
| 安全审计 | NFR-Sec-XX + 定义与约束摘要 + 影响范围 | NFR-Sec-02：敏感操作留痕，影响删除/导出接口 |
| 异常兜底规则 | 异常场景 + 兜底策略 + 提示文案 | 网络异常：保留表单内容，提示"网络异常，请稍后重试" |

### 4.3 好差对比

| | 写法 | 评价 |
| --- | --- | --- |
| 好 | BR-Promo-01：满减互斥规则，影响结算页价格计算逻辑 | 有规则编号、有摘要、有影响范围，未展开全文 |
| 差 | 满减互斥规则是指当用户订单中同时存在满减券和其他促销活动时，系统应优先计算满减金额，若满减后金额低于促销门槛则取消促销资格，该规则适用于结算页的价格计算模块…… | 无规则编号、展开全文、未标明影响范围 |
| 好 | NFR-Auth-01：RBAC + 行级数据权限，影响所有列表查询接口 | 有编号、有摘要、有影响范围 |
| 差 | 权限控制：用户需要登录后才能访问，不同角色看到不同的数据，管理员可以看到所有数据，普通用户只能看到自己的数据…… | 无编号、展开全文、未标明影响范围 |

### 4.4 写作规则

| 规则 | 要求 | 违反后果 |
| --- | --- | --- |
| 必须使用规则编号 | 每条规则写明编号（如 BR-Promo-01、NFR-Auth-01），Feature 文档中未编号的规则分配临时编号（如 BR-TBD-01）并标注"待产品确认编号" | 追溯链断裂，无法从交互契约追溯到规则定义 |
| 必须提供摘要 | 用一句话概括规则定义和约束，不展开全文 | 规则摘要文档臃肿，与 Feature 文档重复 |
| 必须标明影响范围 | 写明该规则影响哪些页面、接口或模块 | 开发无法判断规则的作用边界 |
| 禁止重复展开全文 | 规则全文在 Feature 文档或全局知识库中维护，规则摘要只做引用和摘要 | 违反"引用 + 摘要"核心原则，知识冗余 |

## 5. 落盘前自检清单

以下自检清单在每步落盘前逐项检查。任一条不满足，落盘阻断，重写后重新自检。

### 5.1 自检项

| 序号 | 检查项 | 对应文档字段 | 依据 |
| --- | --- | --- | --- |
| 1 | Step 1 两份文档是否覆盖所有 Story、页面名称一致、HTML 图与文档一致 | 业务流 / 页面映射 | `../step1-功能架构与动线规划/page-mapping.md` 第 5 节、`../shared/design-review.md` |
| 2 | 原型是否含交互说明和异常状态 | 原型文档 - 元素说明 / 异常状态 | `../step2-原型设计与规范对齐/prototype-method.md` 第 5 节 |
| 3 | 交互契约是否有状态机和兜底 | 交互契约 - 状态机 / 异常兜底 | `../step3-交互规则与边界补全/workflow.md` 第 5 节 |
| 4 | 交互规则表的异常兜底列是否采用 GWT 格式 | 交互契约 - 交互规则表 | 本文第 1 节 |
| 5 | 规则摘要是否引用而非重复展开 | 规则摘要 - 全部字段 | 本文第 4 节 |
| 6 | Sprint 是否标注依赖和风险 | 迭代规划 - 风险标注 / 关键依赖 | `../../sprint-planning/workflow.md` 第 4 节（sprint-planning 阶段承担） |
| 7 | 错误提示文案是否具体（非"出错了"等泛词） | 交互契约 - 错误提示 | 本文第 3 节 |
| 8 | 页面映射表的交互说明是否用【】标注页面跳转 | 页面映射 - 页面映射表 | `../step1-功能架构与动线规划/page-mapping.md` 第 4 节 |
| 9 | 核心页面是否有方案对比记录 | 原型文档 - 设计决策记录 | `../step2-原型设计与规范对齐/ui-design-style.md` 第 1 节 |
| 10 | Step 2-3 与迭代规划（sprint-planning 复用）草稿与落盘的 Markdown 是否同结构、同字段、同正文内容 | 原型/交互契约/规则摘要/迭代规划 | 本文第 5.3 节 |

### 5.2 自检流程

1. 逐文档逐字段对照本文件第 1-4 节和 Step 1 两份写作规范检查
2. 逐项确认上表 10 项检查项全部通过
3. 任一项不通过：阻断落盘，修正后重新自检
4. 全部通过后，方可进入落盘流程（见 `persist-guide.md`）
5. 落盘后 `validate-paradigm.sh` 自动校验写作规范，有 `[WARN]` 必须修复后重新落盘

### 5.3 草稿与落盘一致性要求

Step 2-3 与迭代规划（sprint-planning 复用）的对话草稿必须与后续落盘的 Markdown 同结构、同字段、同正文内容。禁止输出摘要版草稿--草稿中省略的字段，落盘时也无法补全。用户看到并确认的必须是完整设计预览，不是摘要草稿。Step 1 无此要求（文件即草稿，见 `persist-guide.md` 第 2 节）。
