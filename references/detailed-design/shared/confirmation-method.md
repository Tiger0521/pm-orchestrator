# 提问与确认方法

本文件在 `mode=draft` 需要与用户确认设计决策时读取。通用交互协议（每轮一题、选项格式、兜底）由主调度器通过 `interactionContract` 传入，详见 `references/orchestrator/output-format.md`；本文件定义 detailed-design 阶段的确认方法，不重复通用协议。

**职责边界**：本文件只管通用确认方法。四个 Step 的 grilling 问答协议（决策域与推导域划分、收敛判据）见 `grilling-protocol.md`（同目录）。

## 1. 提问原则归属

提问原则分散在三处，各司其职，不在本文件重复定义已有内容：

| 位置 | 内容 | 说明 |
| ---- | ---- | ---- |
| `SKILL.md`（主 agent） | 通用交互协议：每轮只问一个问题、选项用大写字母编号、末尾追加"补充描述"和"强制跳过" | 所有阶段共用 |
| `instruction.md`（本阶段） | 提问与确认方法：理解回执、确认流程、问题选择优先级 | 详细设计阶段特有 |
| 需求拆解阶段 | `instruction.md` 追问原则 + grilling 问答 | 详细设计阶段借鉴但不照搬 |

本文件是"提问与确认方法"的权威来源，定义理解回执、确认流程、问题选择优先级和范围漂移防护。通用交互协议以 `SKILL.md` 和 `interactionContract` 为准。

## 2. 理解回执

借鉴需求拆解阶段的"理解回执"原则。每次用户回答后、下一轮确认或提问前，subagent 必须先用 2-5 行反馈当前理解：

```text
已确认：
- 原型方式：交互式 HTML
- 页面映射：订单列表页、退款弹窗、订单详情页
- 核心交互：搜索、筛选、退款申请
待确认：退款弹窗是否需要多步表单（当前按单步设计）
```

回执不是第二个问题，不得夹带新的追问。回执的目的是让用户在下一轮确认前有机会纠偏。如果理解有误，用户先纠偏，再继续。

## 3. 确认流程

四个 Step 各需要用户确认（Step 1 分三阶段各有确认点，见 `../step1-功能架构与动线规划/workflow.md`）。确认不是简单问"对吗？"，而是按以下三段式进行：

1. **先展示结构化产出**（页面映射表 / 原型草案 / 交互规则表 / Sprint 分解方案），每条用加粗关键词领条
2. **再给出理解回执**（已确认了什么、待确认什么）
3. **最后提出一个聚焦问题**（选择题或确认题），遵守每轮一个问题原则

确认问题示例：

| 步骤 | 确认问题 |
| ---- | -------- |
| Step 1 Phase 1（业务流） | "请查看业务流文档：<文件路径>。核心页面层级、系统边界和主干动线是否准确？可直接编辑文件，或告诉我需要修改的地方" |
| Step 1 Phase 2（页面映射） | "请查看页面映射文档：<文件路径>。每条 Story 的页面归属和跳转关系是否准确？" |
| Step 1 Phase 3（HTML 图） | "请用浏览器打开两张图：<架构图路径> 和 <流程图路径>。图的结构、连线与文档是否一致？" |
| Step 2（原型） | "以上原型方案（含布局、交互说明、异常状态）是否符合预期？需要调整哪些页面的设计？" |
| Step 3（交互契约） | "以上交互规则和异常兜底是否覆盖了全部关键路径？有没有规则过严或过松的？" |
| Sprint 分解（sprint-planning 阶段复用） | "以上 Sprint 分解方案是否反映优先级和依赖关系？容量是否合理？" |

> **复用说明**：上表 Step 1-3 属 detailed-design 阶段；「Sprint 分解」确认问题由 sprint-planning 阶段（sprint-planner）复用。

**不得问"对吗？"**：确认问题必须有具体指向。不要问"对吗？""可以吗？""有没有问题？"这种无指向的确认。

**用户确认口径**：只有用户明确说"没问题/确认/可以"（或等义表述）才算确认；"先看看""稍等"不算。用户提出修改时，按反馈修正后再次等待确认。

## 4. 问题选择优先级

如果同一轮有多个待确认项，按以下优先级选择只问一个：

1. 影响后续所有设计的基础决策（原型方式、页面归类）
2. 影响原型质量和交互完整性的设计决策（布局方案、交互规则）
3. 影响异常兜底的异常场景
4. Sprint 分解和依赖排序

## 5. 范围漂移防护

如果用户在确认过程中提出新的页面、新的交互规则或新的 Story 范围，subagent 必须判断是否属于当前设计范围：

- 新页面在已有 User Story 的覆盖范围内 -> 纳入，补充对应设计
- 新交互规则在已有 Feature 的业务规则中 -> 纳入，补充对应交互契约
- 新页面或新规则不在已有 User Story 中 -> 记录到 `tracking-log.md`，标记为"超出当前设计范围，需回到需求拆解阶段补充 Story"，本次不展开

## 6. 交互展示边界

交互展示由主调度器通过 `interactionContract` 统一传入，本阶段不自行定义 UI 或格式规则。

- 每轮只能提出一个需要用户回答的问题或选择题。
- 选择题展示必须遵守主调度器选项协议：业务候选项使用 `A.`、`B.`、`C.`、`D.` 等大写英文字母编号；最后追加"补充描述：我自己填写"和"强制跳过：这个问题暂时不回答，记录为待验证并继续"。不得使用数字、复选框或无编号选项。
- 如果缺少 `interactionContract`，使用简洁 Markdown 问答作为回退，并避免输出 YAML 状态块、绝对路径和长文件清单。

## 7. 确认落账与恢复对账（硬闸）

用户确认（明确说"没问题/确认/可以"或等义表述）后，必须**立即**把该决策写入项目 `decision-log.md`（新增 `D###` 条目）和/或 `facts.json`。未落账的确认对后续会话不可见，等同未确认。

跨会话/续跑时，凡要声称"已确认"的决策（原型方式、UI 风格预设、布局模式、规则兜底等），必须先在本项目 `decision-log.md` / `facts.json` 中找到对应条目；**查无记录一律视为未确认**：向用户重新提出该决策的确认，禁止默认沿用先前假设，禁止把流程内的推荐建议标记为已确认。
