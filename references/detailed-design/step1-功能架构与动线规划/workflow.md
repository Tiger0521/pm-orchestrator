# Step 1 工作流：功能架构与动线规划

本文件是 Step 1 的唯一执行流程。Step 1 分三个阶段顺序推进，每阶段遵循七段式结构（Skill 准备 -> 执行步骤 -> 如何询问 -> 提供什么选择 -> 用户确认点 -> 产出 -> 质量门）。

**职责边界**：本文件只管 Step 1 执行流程。grilling 问答方法见 `../shared/grilling-protocol.md`（Step 1 决策域见其第 3.1 节，推导域见第 4.1 节）；业务流文档写作规范见 `business-flow-writing.md`；页面映射机制与写作规范见 `page-mapping.md`；HTML 图生成要求见 `html-diagram.md`；上游质量门见 `../shared/upstream-quality-gate.md`；确认方法见 `../shared/confirmation-method.md`；定稿落盘步骤见 `../shared/persist-guide.md`。

**三条硬门禁**：

1. **每阶段必须等用户确认**：阶段文件生成并告知路径后返回 `needs-input`，用户明确说"没问题"（或等义确认）前，禁止进入下一阶段。用户提出修改时按反馈修正文件后再次等待确认。
2. **进入下一阶段前必须重读文件**：用户可能直接编辑了产品库中的阶段文件。开始 Phase 2、Phase 3 和定稿前，必须重新读取上一阶段文件，以文件当前内容为准，禁止凭记忆覆盖用户修改。
3. **三阶段全部确认后才定稿**：未完成 Phase 1-3 确认，不得注册 refs.json、更新记忆文件，不得进入 Step 2。

## 2. 阶段定位与会话恢复

subagent 不持有跨轮状态。每次被委派时按以下顺序定位当前位置：

1. 读取过程项目 `docs/_extracted/.design/step1-state.json`（如存在），获取 `phase` 和 `confirmed` 状态
2. 扫描产品库 `详细设计/结构与流程图/` 目录，核对文件实际存在情况
3. 两者冲突时以文件扫描为准（状态文件可能过期），并修正状态文件
4. 无状态文件时按文件存在性判断：无业务流 md -> Phase 1；有业务流无页面映射 -> Phase 2；两份 md 齐但缺 HTML -> Phase 3；全部齐 -> 核对确认状态，未定稿则定稿

`step1-state.json` 结构（写入 `docs/_extracted/.design/`，draft 模式允许写入）：

```json
{
  "step": "step1",
  "phase": "p1-grilling | p1-review | p2-grilling | p2-review | p3-generating | p3-review | finalizing | done",
  "confirmed": {"business_flow": false, "page_mapping": false, "html_diagrams": false},
  "files": {
    "business_flow": "<业务流 md 绝对路径>",
    "page_mapping": "<页面映射 md 绝对路径>",
    "arch_html": "<功能架构图 HTML 路径>",
    "flow_html": "<业务流程图 HTML 路径>"
  },
  "qa_log": [{"round": 1, "phase": "p1", "q": "<润色后的问题>", "a": "<润色后的回答>"}],
  "user_edits": [{"phase": "p1", "note": "<用户直接编辑文件的内容摘要>"}]
}
```

每轮 grilling 问答、用户确认、用户直接编辑文件后，同步更新该 JSON 再返回。

## 3. Phase 1：核心页面层级与系统边界

### 目标

读取上游全部故事，通过 grilling 问答与用户敲定**核心页面层级**、**系统边界**和**功能线业务动线**（每条功能线标注优先级与覆盖 Story，Story 并集 = 全部 User Story），产出业务流文档初稿。

### Skill 准备

- 读取本文件（Step 1 流程）
- 读取 `../shared/grilling-protocol.md`（问答方法，Step 1 决策域见第 3.1 节）
- 读取 `../shared/upstream-quality-gate.md`（上游读取顺序与质量门）
- 读取 `productArchitectureDesignPath`，提取产品事实和总体设计约束

### 执行步骤

1. 按上游质量门读取全部上游文档：
   - 读取 `refs.json`，筛选 `type=user-story` 和 `type=traceability-matrix` 节点
   - 读取所有 User Story 文档的三段式描述、GWT 验收标准、优先级、Story Points
   - 读取溯源矩阵，确认 Story-Feature 映射关系和覆盖度
   - 通过 `refs.json` 追溯到 Feature，读取业务流程、业务规则、用户角色
   - **参考产品库用户故事地图**：扫描 `<产品库产品目录>/用户故事地图/`（如存在），提取用户旅程叙事线、P0 主干行走路径（walking skeleton）、各旅程节点的故事分布；故事地图是页面层级和动线推导的首要素材
   - 检查上游质量门，不通过时返回 `needs-input` 并附缺失字段清单
2. 自主推导页面层级与功能线草案：按 Story 高频共现、故事地图旅程节点、Feature 分组推导一级/二级页面层级和系统边界草案；按端到端业务路径把 Story 聚成功能线草案（每条线覆盖若干 Story，全部功能线的 Story 并集 = 全部 User Story）
3. **grilling 问答**：按 `../shared/grilling-protocol.md` 第 3.1 节与用户逐轮敲定核心页面层级、系统边界与功能线划分（每轮一问、理解回执、事实先查决策再问）
4. 收敛判据满足后（页面层级、系统边界、功能线动线三块均有用户确认结论），按 `business-flow-writing.md` 生成业务流文档：
   - 分配 FLOW 序号（见 `../shared/persist-guide.md` 第 2 节 Step 1 ID 分配）
   - 直接写入产品库 `详细设计/结构与流程图/<简称>-业务流.md`，含完整产品库 frontmatter
   - 业务动线章节按功能线组织（每条线标注优先级与覆盖 Story）；业务流程图章节写入按功能线分 subgraph 的 Mermaid flowchart（Phase 3 再补 HTML 引用）
5. 更新 `step1-state.json`（`phase: p1-review`）
6. **告知用户文件路径**，明确请用户打开文件查看并自行修改，返回 `needs-input` 等待确认

### 如何询问

- grilling 阶段按 `../shared/grilling-protocol.md` 第 3.1 节的问题域逐项敲定，每轮一问
- 文件生成后的确认问题：`请查看业务流文档：<文件路径>。核心页面层级、系统边界和主干动线是否准确？可直接编辑文件，或告诉我需要修改的地方`
- 用户回复修改意见时，修正文件后再次等待确认；用户直接编辑文件时，重读文件确认修改已吸收

### 提供什么选择

页面层级或边界有歧义时提供选择题（选项格式遵守 `interactionContract`）：

```
设备领用能力的入口页面归到哪一级？

A. 独立一级导航"设备管理" -- 领用是高频主操作
B. 归入一级导航"资产中心"的子页 -- 资产统一入口
补充描述：我自己填写
强制跳过：这个问题暂时不回答，记录为待验证并继续
```

### 用户确认点

- 展示理解回执（已读取 Story 数、Feature 数、故事地图主干、已敲定的层级/边界/功能线决策）
- 告知业务流文档路径，请用户看改
- **用户说"没问题"后才进入 Phase 2**；未确认时按反馈修正后重新等待

### 产出

产品库 `详细设计/结构与流程图/<简称>-业务流.md`（含核心页面层级、系统边界、按功能线组织的业务动线、Mermaid 业务流程图）。

### 质量门

- 核心页面层级覆盖全部一级导航和核心页面
- 系统边界明确（包含什么、不包含什么）
- 业务动线按功能线组织：每条功能线从入口到完成完整闭环、标注优先级与覆盖 Story，全部功能线的 Story 并集覆盖全部 User Story
- 业务流程图只含用户操作与页面动线，不涉及底层技术实现

## 4. Phase 2：页面映射

### 目标

在业务流已确认的基础上，通过 grilling 问答理清每条 Story 到页面的映射关系，产出页面映射文档初稿。

### Skill 准备

- **重读业务流文档**（用户可能已直接编辑），以文件当前内容为基准
- 读取 `page-mapping.md`（页面映射机制与写作规范）
- 读取 `../shared/grilling-protocol.md`（问答方法，Step 1 决策域见第 3.1 节）

### 执行步骤

1. 重读业务流文档，识别用户修改；用户修改与已确认结论冲突时先向用户确认
2. 按高频共现、入口出口、跳转关系将 Story 归类到页面，生成页面映射表草案（机制见 `page-mapping.md`）
3. **grilling 问答**：逐项敲定 Story 归属歧义、弹窗与独立页面取舍、入口出口、跳转闭环
4. 收敛判据满足后（每条 Story 有归属页面、无孤儿页面），按 `page-mapping.md` 生成页面映射文档：
   - 沿用 Phase 1 的下一个 FLOW 序号（`<nn>+1`）
   - 直接写入产品库 `详细设计/结构与流程图/<简称>-页面映射.md`，含完整产品库 frontmatter
5. 更新 `step1-state.json`（`phase: p2-review`）
6. **告知用户文件路径**，请用户看改，返回 `needs-input` 等待确认

### 如何询问

- Story 归属有歧义时提供选择题：

```
Story US-Ord-02（退款申请）归到哪个页面？

A. 订单列表页（内嵌弹窗） -- 退款从列表页发起
B. 独立退款页面 -- 退款是独立流程
补充描述：我自己填写
强制跳过：这个问题暂时不回答，记录为待验证并继续
```

- 页面映射表与业务流文档的页面层级不一致时，指出冲突请用户裁决
- 文件生成后的确认问题：`请查看页面映射文档：<文件路径>。每条 Story 的页面归属和跳转关系是否准确？`

### 提供什么选择

- Story 归属选择题（如上）
- 跳转关系取舍选择题（弹窗 / 新页面 / 页内切换）

### 用户确认点

- 展示理解回执（页面数、Story 覆盖度、跳转闭环检查结论）
- 告知页面映射文档路径，请用户看改
- **用户说"没问题"后才进入 Phase 3**

### 产出

产品库 `详细设计/结构与流程图/<简称>-页面映射.md`（含页面映射表、跳转闭环检查、Story 覆盖度）。

### 质量门

- 每条 User Story 都有归属页面
- 页面间跳转关系闭环（没有孤儿页面）
- 页面层级与业务流文档一致
- 页面映射表符合 `page-mapping.md` 的四列表格规范

## 5. Phase 3：结构与流程图 HTML

### 目标

基于已确认的业务流与页面映射，AI 直出生成两张精美的自包含 HTML 图（功能架构图 + 业务流程图），供用户查看确认。业务流程图为**泳道式功能线并行**布局（每条功能线一条泳道、节点常显 Story ID），生成规范见 `html-diagram.md`。

### Skill 准备

- **重读业务流文档和页面映射文档**（用户可能已直接编辑），以文件当前内容为基准
- 读取 `html-diagram.md`（生成要求与美观标准）

### 执行步骤

1. 重读两份 md 文档，从文件当前内容提取图的输入（功能架构图取页面清单、层级分组、Story 归属；业务流程图取功能线清单、各线动线步骤与 Story 归属），并把全部 Story ID 逐条定位到图节点（覆盖度 100% 才可生成，见 `html-diagram.md` 第 4 节生成前映射核对）
2. 按 `html-diagram.md` 生成两张自包含 HTML（每份 md 文档配一张 HTML 图）：
   - 功能架构图：`详细设计/结构与流程图/<简称>-功能架构图.html`（配页面映射文档）
   - 业务流程图：`详细设计/结构与流程图/<简称>-业务流程图.html`（配业务流文档）
3. 按 `html-diagram.md` 第 5 节自查清单逐项检查（含内容零丢失与 Story 覆盖度 100%）
4. 更新 `step1-state.json`（`phase: p3-review`）
5. **告知用户两个 HTML 路径**，请用户浏览器打开查看，返回 `needs-input` 等待确认
6. 用户提出修改时重新生成对应 HTML，再次等待确认

### 如何询问

- 确认问题：`请用浏览器打开两张图：<架构图路径> 和 <流程图路径>。图的结构、连线与文档是否一致？美观上有什么要求？`
- 用户只改其中一张时，只重新生成该张

### 提供什么选择

- 图的布局取向选择题（如自上而下 / 从左到右主流程方向）

### 用户确认点

- 展示理解回执（两张图的节点数、主线、与 md 文档的一致性自查结论）
- **用户说"没问题"后才进入定稿**

### 产出

产品库 `详细设计/结构与流程图/` 下两张自包含 HTML 图。

### 质量门

- 两张 HTML 均已生成且可独立打开（无 CDN、外链字体、外链脚本）
- **内容零丢失**：md 中每条功能线与动线步骤在图中均有对应节点，节点常显 Story ID 且覆盖度 100%（与页面映射表核对），无多画、无漏画
- 符合 `html-diagram.md` 的美观标准与泳道式布局范式

## 6. Step 1 定稿

三阶段全部确认后执行，落盘步骤见 `../shared/persist-guide.md` 第 2 节：

1. **重读全部四份产物文件**，吸收用户的直接编辑
2. 在业务流文档的业务流程图章节补流程图 HTML 引用；在页面映射文档补功能架构图 HTML 引用
3. 注册 `refs.json` 节点（两份 md，含 `libraryId`/`path`/`contentHash`）和引用边（业务流/页面映射 references User Story）
4. 更新记忆文件（`facts.json`、`decision-log.md`、`tracking-log.md`、`phase-summary.md`）
5. 运行 `validate-paradigm.sh` 校验两份 md，有 `[WARN]` 时修复后重跑，零警告才算定稿
6. 更新 `step1-state.json`（`phase: done`），返回 `draft-ready`（Step 1 完成，可进入 Step 2）

## 7. sourceProduct 直启

handoff 含 `sourceProduct` 时（见 `instruction.md` 只读来源产品路由）：上游读取来源产品的 Story、设计、能力文档和 `用户故事地图/`（如存在）作为只读输入；**三份产物与其他项目一致直接写入产品库来源产品目录的 `详细设计/结构与流程图/`**，不以过程项目为中间落点；定稿按第 6 节正常执行（含 refs 注册与校验）。只读约束仅针对来源产品的已有文档，新设计文档的写入不受限制。

## 8. 规模自适应差异

- `new` 项目：完整执行三阶段
- `iteration` 项目：Phase 1 读取已有业务流/页面映射文档作为基线，聚焦新增 Story 的层级扩展和归属增量；HTML 图按更新后的全量内容重新生成
- `refactor` 项目：读取 `productLibraryDocsPath` 下已有设计作为只读基线，保持已有页面映射不变，只产出受影响部分的变更说明；详见 `../shared/scale-adaptation.md`
