# 用户故事地图核心机制

## 1. Jeff Patton 用户故事地图模型

用户故事地图（User Story Mapping）由 Jeff Patton 提出，核心思想是把用户故事组织成一张二维地图：

- **横轴（水平方向）= 用户旅程**：故事按用户完成业务目标的流程步骤从左到右排列。横轴有时间方向性，读者可以从左到右"走"完一条完整的用户路径。
- **纵轴（垂直方向）= 优先级**：同一旅程步骤内的故事按重要性从上到下排列。最上层是 MVP 必做故事，往下是体验增强和运营支持。

### 1.1 地图的三层切面

| 层级 | 名称 | 含义 | 在矩阵中的位置 |
| --- | --- | --- | --- |
| 第一层 | MVP 核心（P0） | 最小可行产品必做故事，构成主干行走路径 | 矩阵最上行 |
| 第二层 | 体验增强（P1） | 提升用户体验的增强功能 | 矩阵中间行 |
| 第三层 | 运营支持（P2） | 长期运营支持功能 | 矩阵最下行 |

### 1.2 行走路径（Walking Skeleton）

行走路径是地图最上层（P0）从左到右的一条连贯路径，代表用户完成核心业务目标所需的最小故事集合。行走路径必须满足：

- **连贯性**：从旅程第一步到最后一步，每一步至少有一条 P0 故事覆盖。
- **完整性**：行走路径上的故事集合构成一个可独立交付的 MVP。
- **可走性**：读者可以从左到右读完行走路径，理解用户如何完成核心业务目标。

## 2. 2D 矩阵概念

故事地图的核心视觉形态是**二维网格**，而非一维列表。矩阵结构如下：

```
              横轴：用户旅程阶段（从左到右）
              ┌──────────┬──────────┬──────────┬──────────┐
   P0 MVP核心 │ ⭐ 故事A  │ ⭐ 故事D  │ ⭐ 故事F  │ ⭐ 故事H  │  ← 行走路径
              ├──────────┼──────────┼──────────┼──────────┤
   P1 体验增强 │  故事B   │          │  故事G   │          │
              ├──────────┼──────────┼──────────┼──────────┤
   P2 运营支持 │  故事C   │  故事E   │          │  故事J   │
              └──────────┴──────────┴──────────┴──────────┘
               阶段1      阶段2      阶段3      阶段4
```

### 2.1 矩阵单元格

每个单元格代表"某个旅程阶段 × 某个优先级"的交叉点，可能包含 0 到 N 条故事。空单元格表示该阶段在该优先级没有故事覆盖，可能是覆盖空白。

### 2.2 矩阵的两个层级

| 层级 | 文件 | 横轴 | 纵轴 | 单元格内容 |
| --- | --- | --- | --- | --- |
| 总览地图 | 总览文件 | 全局旅程阶段（如：建址/维址/用址/治址/运址） | P0/P1/P2 | 各能力的故事卡片摘要 |
| 能力级地图 | 各能力文件 | 能力内旅程节点（如：补全/录入/校验/审核/核准） | P0/P1/P2 | 该能力的具体故事卡片 |

总览地图的横轴是全局旅程阶段，所有能力的故事对齐到统一阶段。能力级地图的横轴是该能力内部的旅程节点，提供更细粒度的视图。两个层级通过 wikilink 关联。

## 3. 故事卡片要素

每条故事在矩阵中以"故事卡片"形式呈现。故事卡片包含以下要素：

| 要素 | 说明 | 来源 |
| --- | --- | --- |
| 故事标题 | 简短描述故事内容 | 用户故事文件的 title 或文件名 |
| 故事链接 | wikilink 指向故事详情文件 | 用户故事文件路径 |
| 角色 | 参与该故事的用户角色 | 能力文档的用户角色 + 故事描述 |
| 核心价值 | 一句话描述该故事的业务价值 | 故事描述中的"以便于..."部分 |
| 旅程位置 | 该故事在旅程线中的位置 | 由旅程阶段和旅程节点共同确定 |
| 优先级 | P0/P1/P2 | 故事文件的 frontmatter 或能力文档 |

在总览地图的矩阵单元格中，故事卡片以紧凑形式呈现（标题 + wikilink + 角色）。在能力级地图中，故事卡片以完整形式呈现（全部要素）。

## 4. 优先级分层规则

### 4.1 优先级来源

故事优先级的确定顺序：

1. 如果用户故事文件的 frontmatter 中有明确的 `priority` 字段，直接使用。
2. 如果没有，从能力文档中的"优先级"字段推断该能力下所有故事的默认优先级。
3. 如果两者都没有，标记为"待确认"，向用户询问。

### 4.2 优先级校验

- 每条故事必须且只能属于一个优先级层级。
- P0 故事必须构成行走路径（每条 P0 故事都在旅程线上有明确位置）。
- 如果某个旅程阶段没有任何 P0 故事，标记为"行走路径断裂"，向用户确认是否需要补充。

## 5. 跨能力关联

### 5.1 旅程阶段对齐

不同能力的故事需要对齐到统一的全局旅程阶段。对齐规则：

1. 从设计文档的"核心场景"提取全局旅程阶段（通常 3-6 个阶段）。
2. 将每个能力映射到一个或多个旅程阶段（一个能力可能跨越多个阶段）。
3. 将每条故事按其所属能力和业务流程映射到具体的旅程阶段。

### 5.2 能力间衔接标注

在总览地图中，用标注标识能力间的衔接关系：

- **顺序衔接**：能力 A 的输出是能力 B 的输入（如：创建能力产出的地址供查询能力使用）。
- **反馈衔接**：能力 B 的结果反馈给能力 A（如：纠错能力发现问题反馈给维护能力修复）。
- **并行覆盖**：能力 A 和能力 B 在同一旅程阶段并行提供不同价值。

衔接标注在总览地图的"跨能力关联"章节中以表格形式呈现，不使用 ASCII 画图。

## 6. 旅程叙事线

### 6.1 全局叙事线

全局叙事线是贯穿整个产品的用户旅程主线，从设计文档的核心场景推导。叙事线用一句话描述每个阶段的目标：

> 用户需要地址 -> 创建地址 -> 维护地址 -> 使用地址 -> 治理地址质量 -> 运营监控

### 6.2 能力级叙事线

每个能力有自己的子旅程线，描述用户在该能力内的操作流程。能力级叙事线从能力文档的"业务流程"字段提取：

> 补全/解析 -> 录入/导入 -> 校验查重 -> 审核 -> 核准消歧

### 6.3 叙事线与矩阵的关系

叙事线定义了横轴的方向和节点；矩阵把故事放置到横轴节点 × 纵轴优先级的交叉点上。叙事线不是独立的 ASCII 图，而是通过矩阵的列标题直接体现。

## 7. 质量自检

生成地图后，按以下清单自检：

1. **矩阵形态**：地图是否呈现为二维表格（行列交叉），而非一维列表？
2. **横轴方向**：横轴是否有明确的从左到右的旅程方向？
3. **行走路径**：P0 行是否构成从左到右的连贯路径？有无断裂？
4. **故事覆盖**：每个旅程阶段是否至少有一条故事？空单元格是否标注为覆盖空白？
5. **能力对齐**：所有能力是否都映射到了全局旅程阶段？
6. **数据一致**：总览地图的故事数量与各能力级地图的故事数量之和是否一致？
7. **链接有效**：wikilink 指向的故事文件是否实际存在于产品库中？
8. **优先级完整**：每条故事是否都有明确的 P0/P1/P2 归属？

如果任一项不通过，不得输出 `map-draft-ready`，需修正后重新展示。
