# 旅程叙事线提取指南

本指南定义旅程叙事线的提取来源与提取方法。**旅程叙事线的唯一来源是业务文档（`businessDocPath`）的「业务场景表」（SC-XX 编号，含「所属能力」列）**；不再从架构设计文档的核心场景推导旅程阶段。业务文档是扁平 4 字段结构（不按能力分章节），能力信息在场景表/规则表的「所属能力」列，提取时按该列分组。

## 1. 从业务场景表提取能力内旅程节点

### 1.1 提取来源

| 提取对象 | 位置 | 提取内容 |
| --- | --- | --- |
| 能力内旅程节点 | 业务文档「业务场景」字段下的业务场景表（场景编号 SC-XX + 所属能力列） | 按「所属能力」列分组后，每组场景的业务场景与流程步骤 |

### 1.2 提取方法

1. **定位业务场景表**：在业务文档「业务场景」字段下找到业务场景表；表中每条场景带 `SC-XX` 编号（如 `SC-01`、`SC-02`）和「所属能力」列。
2. **按所属能力分组**：以「所属能力」列与产品库 Feature 能力名对齐，将场景行按能力分组；每个能力一组场景，是该能力内旅程节点的素材。
3. **识别流程步骤**：逐条读取组内场景描述，识别用户在该场景中的关键操作步骤。
4. **聚类为能力内旅程节点**：将细粒度步骤聚类为该能力内的 3-8 个旅程节点。聚类原则：
   - 每个节点有一个明确的用户目标。
   - 节点之间有先后关系（前一个节点的输出是后一个节点的输入）。
   - 节点名称简短（2-4 个字），使用动宾结构（如"补全/解析""录入/导入""校验查重""审核""核准消歧"）。
5. **排序节点**：按用户完成能力内业务目标的时间顺序从左到右排列。
6. **撰写节点描述**：为每个节点写一句话描述，说明用户在该节点要完成什么。

### 1.3 提取示例

业务文档业务场景表摘录（同一能力 SC-01~SC-05 为一组，其余能力场景同理分组）：

| 场景编号 | 业务场景 | 所属能力 | 流程步骤 |
| --- | --- | --- | --- |
| SC-01 | 用户提交地址信息，系统智能解析补全 | 地址创建与审核能力 | 提交地址 -> 系统解析 -> 补全缺项 |
| SC-02 | 用户录入或批量导入地址数据 | 地址创建与审核能力 | 录入 -> 导入 -> 数据整理 |
| SC-03 | 系统校验地址格式并查重 | 地址创建与审核能力 | 校验格式 -> 查重比对 |
| SC-04 | 审核人员审核地址 | 地址创建与审核能力 | 提审 -> 审核通过/驳回 |
| SC-05 | 核准入库，含歧义消歧 | 地址创建与审核能力 | 核准 -> 消歧 -> 入库 |

提取结果（该能力内旅程节点）：

```
补全/解析 -> 录入/导入 -> 校验查重 -> 审核 -> 核准消歧
```

## 2. 对齐全局旅程叙事线

### 2.1 对齐方法

1. 收集全部能力（按所属能力列分组）的旅程节点后，将语义相近的节点聚类为 3-6 个**全局旅程阶段**。
2. 每个全局阶段有一个明确的用户目标，阶段之间保持先后关系。
3. 一个能力可能跨越多个全局阶段，在能力覆盖矩阵中标注"主要"和"辅助"。
4. 全局阶段命名简短（2-4 个字）、动宾结构（如"建址""维址""用址""治址""运址"）。

### 2.2 对齐决策表

| 能力旅程节点的业务场景关键词 | 推荐全局阶段 |
| --- | --- |
| 创建、录入、导入、审核、核准 | 建址 |
| 维护、修改、状态、启用、停用、废弃 | 维址 |
| 查询、搜索、选址、详情、API、校验 | 用址 |
| 质量、治理、合并、标准化、纠偏、纠错、反馈 | 治址 |
| 监控、运营、看板、告警、统计、分析 | 运址 |
| 变更、事件、推送、订阅、同步 | 维址（或独立"同步"阶段） |
| 迁移、区划、批量 | 维址（或独立"迁移"阶段） |

### 2.3 特殊情况处理

- **一个能力跨越多个阶段**：在覆盖矩阵中标注"主要"和"辅助"。该能力下 Story 的 `journey_stage` 按各自业务目标落到对应阶段，不强行归一到单一阶段。
- **一个全局阶段没有能力覆盖**：标记为"覆盖空白"，向用户确认是否需要调整阶段划分。
- **能力无法对齐到任何阶段**：向用户确认该能力的旅程归属，或考虑新增旅程阶段。
- **场景表的所属能力列与 Feature 能力名不一致**：以产品库 Feature 能力名为准，向用户确认该场景归属后再分组。

## 3. Story 归属映射（journey_stage）

旅程叙事线确认后，每条 Story 必须回填 `journey_stage`：

1. 在拆解该能力下的 Feature 时，结合 Story 的用户目标，选择它落实的全局阶段与能力内节点。
2. `journey_stage` 值格式：`<全局旅程阶段>-<能力内节点>`（如 `建址-审核核准`）；当能力仅映射单一全局阶段时可简写为全局阶段名（如 `维址`）。
3. 值必须属于已确认旅程叙事线的节点白名单；跨阶段 Story 取其核心动作对应的节点，不编造新节点。
4. `journey_stage` 写入 Story frontmatter、Story JSON 顶层字段与溯源矩阵的"旅程阶段"列，是地图组装的直接依据。

## 4. 旅程确认问题模板

旅程节点与全局叙事线提取完成后，向用户确认：

```
基于业务文档业务场景表（SC-XX，按所属能力列分组），我提取了以下旅程节点与全局叙事线：

| 全局阶段 | 能力内节点 | 对应能力 | 一句话描述 |
| --- | --- | --- | --- |
| 建址 | 补全/解析 -> 录入/导入 -> 校验查重 -> 审核 -> 核准消歧 | 地址创建与审核能力 | ... |
| 维址 | ... | 地址维护能力、变更事件能力 | ... |
| ... | ... | ... | ... |

这个旅程节点与全局阶段划分是否合理？

A. 合理，继续拆解 Story
B. 需要调整阶段或节点数量/名称（请说明）
补充描述：我自己填写
强制跳过：这个问题暂时不回答，记录为待验证并继续
```
