# 提问与确认方法

本文件在 `mode=draft` 需要与用户确认 story-map 阶段决策时读取。通用交互协议（每轮一题、选项格式、兜底）见 `references/orchestrator/output-format.md`，本文件定义本阶段的确认方法。

用户选定候选 Story 后的决策问题、推荐答案、依赖顺序、共同理解门禁与 JSON 状态更新一律以 `grilling-protocol.md` 为准；本文件只处理候选选择前和共同理解后各阶段产出的展示与确认，不重复盘问规则。确认内容显式覆盖旅程阶段（`journey_stage`）与台账关联（`requirementEntryId`），不把两条新字段当作"无需确认的收尾项"。

## 理解回执

每次用户回答后、下一轮确认或提问前，必须先用 2-5 行反馈当前理解。回执以"当前故事或本步产出"为主体，让用户看到它现在长什么样、哪里未定，而不是抽象罗列已确认/待确认清单：

```text
当前故事 · story-001：
作为 算法工程师，我想要 创建模型配置，以便于 __无需重启即生效（价值待澄清）__。
GWT 草稿：成功创建 / 必填项校验 / 重复名称 / __权限场景未明__。
旅程阶段：建址-审核核准 | 台账条目：网资-REQ-001（P0）
待澄清：第 4 条权限场景的预期结果。
```

回执不是第二个问题，不得夹带新的追问。回执的目的是让用户在下一轮确认前有机会纠偏。如果理解有误，用户先纠偏，再继续。

## 确认流程

工作流中，第 1 步旅程确认、第 2 步角色规则、第 3a 步候选总表选择、每组 Feature 三块内容审阅、第 4 步地图方案确认，以及整批落盘确认需要用户确认。第 3a 步用于选择讨论范围；每组 Feature 的三块内容审阅先完成 `grilling-protocol.md` 的三块内容审阅，再在这里确认相应产出。确认不是简单问"对吗？"，而是：

1. 先展示结构化产出（旅程叙事线与能力映射 / 角色-规则摘要 / 候选总表 / 当前这一个 Feature 组的完整 Story 草稿清单 / 地图方案 / 完整落盘预览），每条用加粗关键词领条。**一次只展示一个 Feature 组**，组内每条 Story 的三块内容（三段式 / GWT / 边界异常）完整写出原文，不缩写、不省略。
2. 再给出理解回执（已确认了什么、待确认什么）。
3. 最后提出一个聚焦问题（选择题或确认题），遵守每轮一个问题原则。

确认问题示例：

| 步骤 | 确认问题 |
| ---- | -------- |
| 第 1 步（旅程提取） | "以上旅程节点与全局阶段划分是否合理？各能力映射是否准确？" |
| 第 2 步（角色规则） | "以上角色和规则覆盖了本次拆解的全部用户场景，还是需要补充？" |
| 第 3a 步（候选总表） | "以上候选分别由哪个能力拆出已标明。请选本轮值得深入讨论的一个或多个标签（如 A、C、F）；哪些暂不讨论？" |
| 第 3b 步（按 Feature 分组审阅） | "这一组 Feature 的 Story 草稿（三段式 / GWT / 边界异常 + 自动优先级、SP、旅程阶段、台账条目）是否准确？要调整或合并哪些？" |
| 第 4 步（地图方案） | "这份能力级地图的矩阵布局、行走路径与跨能力衔接是否准确？要调整哪些？" |
| 整批确认 | "全部 Feature 的 Story 方案、旅程阶段、台账条目关联、溯源矩阵覆盖度与地图方案是否确认？要调整哪些？" |

不得问"对吗？"：确认问题必须有具体指向，例如"需要调整或合并哪些？""有没有遗漏？""标准是否过严或过松？"。不要问"对吗？""可以吗？""有没有问题？"这种无指向的确认。

确认后按 `grilling-protocol.md` 更新 Story JSON 中相应决策组的 `shared_understanding` 和 `decision_tree` 状态。用户提出修改时，受影响节点保持 `pending`，下一轮只问其依赖已满足的直接缺口。

## 阶段性确认优先级

只有组审阅已收敛三块内容、同一轮仍有多个阶段性确认项时，按以下优先级选择只问一个：

1. 影响后续所有拆解的基础决策（旅程叙事线、角色）。
2. 影响 Story 数量和颗粒度的拆分方案。
3. 影响验收标准的边界异常。
4. 影响 Story 归位与追溯的旅程阶段、台账条目关联。
5. 整批 Story 拆解方案、地图方案确认。

优先级、估算与溯源矩阵为自动附带项，不逐条确认。

## 范围漂移防护

如果用户在确认过程中提出新的角色、新的异常场景、新的旅程节点或新的 Feature 范围，必须判断是否属于当前拆解范围：

- 新角色在已有 Feature 的用户角色字段中：纳入，补充对应 Story。
- 新异常场景在已有 Feature 的业务规则中：纳入，补充对应 AC。
- 新旅程节点能由业务文档业务场景表（SC-XX，含所属能力列）支撑：增量并入旅程叙事线，写入 `phase-summary.md`，纳入对应 Story 的 `journey_stage` 白名单。
- 新角色、新场景或新旅程节点不在已有 Feature/业务场景表中：写入当前 Story JSON 的冲突/范围记录，标记为"超出当前拆解范围，需回到需求分析阶段补充 Feature 或业务场景"，返回主调度器；本次不展开，也不得在 `draft` 模式写入 `tracking-log.md`。
- 台账条目缺失或优先级未定时不得使用 Feature 优先级替代；回到需求分析补登条目，或标"待确认"询问用户裁决。
