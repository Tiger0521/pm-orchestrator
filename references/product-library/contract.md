# 产品库落盘契约

本文件只定义产品库定位、目录、命名、内容和脚本职责。产品匹配读取 `references/requirement-analysis/guides/product-matching.md`；实现细节由脚本承载。

## 1. 定位与身份

自动发现从终端当前目录开始查找固定容器 `product-library/`：检查当前目录；未找到时逐级向上，最多检查 3 个父目录。找到后，把其中包含唯一匹配 `^.+架构设计\.md$` 的根文档的一级子目录列为可用产品库；没有候选时只允许从 Git 仓库获取，或由用户提供已有产品库的本地路径。显式提供的路径不受自动发现容器限制。产品库不由本 Skill 创建；无论来源如何，都只以该正则和唯一性为准。

```text
<workspace-or-parent>/
└── product-library/
    ├── 网络资源中心产品库/网络资源中心产品库架构设计.md
    └── 运维监控产品库/运维监控产品库架构设计.md
```

匹配 `^.+架构设计\.md$` 的唯一文件是产品库根标识和最高产品设计标准。产品库目录名由提供方定义，使用中文且不得包含空格、路径分隔符或文件系统禁用字符。

## 2. 产品简称

- 产品目录使用产品全名，产品文件使用简称前缀。
- 产品全名使用 `简称：描述` 格式：2–6 个汉字的简称作前缀，全角冒号 `：` 分隔，冒号后是描述部分（汉字）。半角冒号 `:` 是 Windows 文件系统禁用字符，必须用全角 `：`。
- 简称由产品负责人定义，必须是 2–6 个汉字，在同一产品库内唯一，且必须等于产品全名中冒号前的部分。
- 全名与简称登记在匹配根文档的产品矩阵区域后才允许创建产品目录。

产品矩阵使用 HTML 注释标记区域，每个产品对应一个 `## 产品全名` 标题和一个 `<!-- product:产品全名:start/end -->` 标记块：

```markdown
<!-- product-matrix:start -->
## 网资：网络资源全生命周期管理

产品概述（导出时从 Epic 产品定位提取，之后手动维护）...

<!-- product:网资：网络资源全生命周期管理:start -->
**简称**：网资

### 能力索引

#### 设备领用能力
- [[网资-设备领用能力-能力文档|设备领用能力]]

### 故事索引

#### 设备领用能力
- [[网资-设备领用能力-提交领用申请故事|提交领用申请]]

<!-- product:网资：网络资源全生命周期管理:end -->
<!-- product-matrix:end -->
```

标记块内由脚本自动维护简称、能力索引和故事索引；标记块外的标题和概述由用户手动维护，首次导出时由脚本从 Epic 产品定位提取。能力索引和故事索引按父能力分组（`#### 父能力名`），叶子能力以自身名分组。

## 3. 目录结构

```text
product-library/<产品库名称>/
├── <匹配 ^.+架构设计\.md$ 的根文档>
└── <产品全名>/
    ├── <简称>-需求卡片.md
    ├── <简称>-设计文档.md
    ├── <叶子能力>/
    │   ├── <简称>-<叶子能力>-能力文档.md
    │   └── 用户故事/<简称>-<叶子能力>-<故事标题>故事.md
    ├── <父能力>/
    │   └── <子能力>/
    │       ├── <简称>-<父能力>-<子能力>-能力文档.md
    │       └── 用户故事/<简称>-<父能力>-<子能力>-<故事标题>故事.md
    └── 详细设计/
        ├── 结构与流程图/<简称>-DF-FLOW<nnn>.md
        ├── 原型/<简称>-DF-PROTO<nnn>.md
        ├── 交互契约/<简称>-DF-CONTRACT<nnn>.md
        ├── 规则摘要/<简称>-DF-RULES<nnn>.md
        └── 迭代规划/<简称>-DF-SPRINT<nnn>.md
```

能力目录必须以“能力”结尾。导出脚本会对过程文档中的每一级能力名自动补齐“能力”后缀，不改写过程文档标题；补齐后出现同一能力路径的多个 Feature 时阻断导出。叶子能力放 1 份能力文档和 `用户故事/`，不能有子能力；父能力只放一个或多个子能力目录，不能放能力文档或 `用户故事/`。当前契约只允许一层父能力和一层子能力。

## 4. 命名

产品全名（目录名）用中文加全角冒号 `：`（见第 2 节）；能力目录名和文件名用中文加半角中划线 `-`。半角冒号 `:` 属 Windows 文件系统禁用字符，须用全角 `：`。所有名称不得包含空格、路径分隔符或其他文件系统禁用字符。

- 需求卡片：`简称-需求卡片.md`
- Epic 设计文档：`简称-设计文档.md`
- 顶层叶子能力文档：`简称-能力-能力文档.md`
- 子能力文档：`简称-父能力-子能力-能力文档.md`
- 顶层叶子能力故事：`简称-能力-故事标题故事.md`
- 子能力故事：`简称-父能力-子能力-故事标题故事.md`
- 结构与流程图：`简称-DF-FLOW<nnn>.md`（位于 `详细设计/结构与流程图/`）
- 原型：`简称-DF-PROTO<nnn>.md`（位于 `详细设计/原型/`）
- 交互契约：`简称-DF-CONTRACT<nnn>.md`（位于 `详细设计/交互契约/`）
- 规则摘要：`简称-DF-RULES<nnn>.md`（位于 `详细设计/规则摘要/`）
- 迭代规划：`简称-DF-SPRINT<nnn>.md`（位于 `详细设计/迭代规划/`）
- 根标识：唯一匹配 `^.+架构设计\.md$` 的根文档

用户故事文件名使用“故事标题故事”后缀，不使用序号；标题仅可包含中文、英文字母、数字和单个中划线。导出时会将同一能力下、标题匹配的旧序号或旧无后缀文件改名为新文件名；若故事标题重复，则阻断导出。

## 5. Frontmatter

除匹配正则的产品库根文档外，每份 Markdown 必须包含 `id`、`product`、`type`、`aliases` 和 `tags`；能力文档和用户故事还必须包含 `capability`。

```yaml
---
id: "网资-EPIC-F01"
product: 网络资源全生命周期管理
type: 能力文档
capability: 设备领用能力/领用审批能力
aliases:
  - 设备领用能力/领用审批能力
tags:
  - 网资
  - 能力文档
  - 设备管理能力/领用审批能力
---
```

`type` 只允许 `需求卡片 | 设计文档 | 能力文档 | 用户故事 | 业务流 | 页面映射 | 结构流程图 | 原型 | 交互契约 | 规则摘要 | 迭代规划`。`capability` 使用相对于产品目录的能力路径，不包含产品目录名。`aliases` 和 `tags` 均为 YAML 列表，由渲染脚本自动注入。`id` 使用继承式产品库 ID（格式见 `references/shared/traceability-model.md` 的"产品库 ID"章节）。产品库不得保留过程空间的 `projectId`、`refs` 或 `status`。`id` 字段是产品库 ID，不是过程 ID。校验脚本会拒绝 frontmatter `id` 字段以外的过程 ID。

`aliases` 和 `tags` 的取值规则：

| 文档类型 | aliases | tags |
| --- | --- | --- |
| 需求卡片 | `[产品全名]` | `[简称, 需求卡片]` |
| 设计文档 | `[产品全名]` | `[简称, 设计文档]` |
| 能力文档 | `[能力路径]` | `[简称, 能力文档, 能力路径]` |
| 用户故事 | `[能力路径 故事标题]` | `[简称, 用户故事, 能力路径]` |
| 业务流 | `[产品全名 业务流]` | `[简称, 业务流]` |
| 页面映射 | `[产品全名 页面映射]` | `[简称, 页面映射]` |
| 结构流程图 | `[产品全名 结构流程图]` | `[简称, 结构流程图]` |
| 原型 | `[产品全名 原型]` | `[简称, 原型]` |
| 交互契约 | `[产品全名 交互契约]` | `[简称, 交互契约]` |
| 规则摘要 | `[产品全名 规则摘要]` | `[简称, 规则摘要]` |
| 迭代规划 | `[产品全名 迭代规划]` | `[简称, 迭代规划]` |

`tags` 中的能力路径使用 `/` 分隔（如 `设备管理能力/领用审批能力`），在 Obsidian 中形成嵌套标签。`aliases` 中的能力路径同样使用 `/` 分隔。

## 6. 文档映射与 Obsidian

- 需求卡片映射为 `简称-需求卡片.md`。
- Epic 映射为 `简称-设计文档.md`，并承担产品概览职能。
- Feature 映射为对应叶子能力的能力文档。
- User Story 和 GWT 映射到对应叶子能力的 `用户故事/`。
- 结构与流程图映射为 `详细设计/结构与流程图/简称-DF-FLOW<nnn>.md`。
- 业务流映射为 `详细设计/结构与流程图/简称-DF-FLOW<nnn>-业务流.md`（详细设计 Step 1 直写，含 ID/frontmatter）。
- 页面映射映射为 `详细设计/结构与流程图/简称-DF-FLOW<nnn>-页面映射.md`（详细设计 Step 1 直写，与业务流共用 FLOW 序号连续分配）。
- 功能架构图与业务流程图 HTML 映射为 `详细设计/结构与流程图/简称-DF-FLOW<nnn>-架构图.html`、`简称-DF-FLOW<nnn>-流程图.html`（与配套 md 文档同序号）。
- 原型映射为 `详细设计/原型/简称-DF-PROTO<nnn>.md`。
- 交互契约映射为 `详细设计/交互契约/简称-DF-CONTRACT<nnn>.md`。
- 规则摘要映射为 `详细设计/规则摘要/简称-DF-RULES<nnn>.md`。
- 迭代规划映射为 `详细设计/迭代规划/简称-DF-SPRINT<nnn>.md`。
- 详细设计五类按文档类型独立编号，跨能力产物归入对应类型子目录，不按能力分组。
- 使用 `[[文件名]]` 或 `[[文件名|显示文本]]` 建立链接，不写扩展名；同名历史文件使用带路径链接兜底。**注意：表格单元格内的别名链接必须转义管道符（`[[文件名\|显示文本]]`），禁止写未转义的 `[[文件名|显示文本]]`，否则 `|` 会被当作表格列分隔符导致链接错位。**
- 导出脚本自动注入 `aliases` 和 `tags`；`product` 字段用于搜索和图谱分组，`tags` 用于标签过滤，`aliases` 用于别名链接。
- 校验脚本检测全库同名文件和别名冲突。

产品库是正式资产，`mode=persist` 时直接写入产品库。过程空间只保留草稿态数据（字段 JSON、故事 JSON、背景材料）和项目记忆文件。不再有独立的导出步骤。

## 7. 脚本职责

- `acquire-product-library.sh`：从 Git 仓库克隆或更新产品库，或规范化用户提供的已有本地产品库路径；不创建空产品库、不复制本地库、不执行 `git init`。
- `validate-product-library-lite.sh`：快速确认产品库身份（路径存在、唯一架构设计文件、至少一个产品目录），不逐文件校验。正常流程第 0 步使用此脚本。
- `validate-product-library.sh`：全量校验目录、简称、命名、frontmatter（含 `id` 必填与格式校验、`aliases`/`tags` 格式）、层级、文件名唯一性、别名冲突和链接完整性。按需手动执行。
- `export-to-library.sh`：已废弃。persist 直接写入产品库，不再需要导出步骤。旧项目迁移使用 `backfill-library-ids.mjs`。
- `render-doc.sh`：把字段 JSON 渲染为 Markdown 写入产品库产品目录；支持需求卡片/Epic/Feature 与详细设计五类（结构流程图/原型/交互契约/规则摘要/迭代规划），按继承式产品库 ID 规则分配或复用 ID，渲染后自动运行 `validate-paradigm.sh`。详细设计五类写入 `详细设计/<类型子目录>/`。
- `product-library-tools.mjs reconcile`：扫描产品库、计算 SHA-256 哈希、比对 `refs.json`、输出变更报告、更新哈希。
- `rename-product.sh`：预览简称变更，确认后批量改名、更新链接和产品矩阵标记区域，失败时回滚。

改简称默认只预览；只有用户确认后才使用 `--apply`。写入后必须校验。简称变更前校验格式与唯一性，`product` 始终保存产品全名。
