# 需求台账写作范式

> 前置读取：本文件与 `templates/requirement-ledger.md` 配套。写台账草稿前先读模板，再按本文件规范撰写。
>
> **定位**：需求台账是按"小功能"登记需求条目的**表格台账**，从拆解 Feature 时开始存在。条目在 features 批次逐个能力拆解产生（每个能力拆 2-N 条小功能），后续每次新增、修改、废弃需求都追加新行。**追加式，不覆盖已有行。**

---

## 粒度阶梯

**能力(Feature) > 需求条目(小功能) > 用户故事(Story)**：

- **比能力小**：一个能力拆成 2-N 个彼此独立、可单独描述、可单独排优先级的小功能；"整能力"不能是一条条目；若一条需求内容还能再拆出多个独立功能点，则继续拆。
- **比故事大**：一条条目通常由多条故事实现（主路径 + 异常/边界故事共同落实一个小功能）；故事仍按"一个 Story 能独立完成测试"的细粒度标准拆。
- **判断信号**：一句话说完且一条故事就能实现 → 太细，做进故事层；还能再拆出多个独立功能点 → 再拆。拆解时逐能力与用户确认条数与粒度。

## 表格格式

每行一条目，六列固定：

| 列 | 写法 |
| --- | --- |
| 条目ID | `<产品简称>-REQ-<三位序号>`（如 `网资-REQ-001`），产品内唯一、连续累加，不随废弃回收；追加时取表内最大序号 +1 |
| 登记日期 | 条目登记日期 `YYYY-MM-DD` |
| 登记人 | 登记该条目的角色/人名；默认取需求卡片"提出人/角色"，用户可改 |
| 所属Feature | 能力名 + 能力文档产品库 ID，如 `设备领用能力（网资-EPIC-F01）`；一个条目只属于一个 Feature |
| 优先级 | `P0 / P1 / P2`，全流程优先级的唯一来源；同一能力下不同条目可不同 |
| 需求内容 | 见下"需求内容写作规范" |

## 需求内容写作规范

需求内容是**清晰自包含的描述，不是标题式短句**：

- **差**：`提供API地址查询`
- **好**：`**标准API地址查询与事件订阅**：对外提供地址查询API（精确/模糊/分页），返回标准结构化地址；支持订阅事件推送，供各业务系统渐进式接入；无需业务侧各自维护地址文本`

结构：`**功能名**：做什么（核心动作与产物）+ 给谁用/在什么场景用 + 关键组成或边界（1-3 点）`，2-4 句。不用三段式"作为…需要…以便…"，不写验收要点（GWT 留给用户故事阶段）。判断标准：不依赖上下文、单独读这一格就能知道这个小功能要做什么、做到什么程度。

## 条目生成规范（features 批次）

拆解每个 Feature 字段确认后（见 `workflows/draft.md` 第 8.5 步）：

1. 按粒度阶梯追问该能力下的小功能条数与每条内容（`../guides/question-bank.md` → "Feature 小功能拆解追问"）。
2. 每条生成一行草稿（六列齐全）；条目 ID 从现有台账表取最大序号 +1；登记人默认需求卡片"提出人/角色"。
3. 优先级给建议值（P0/P1/P2），由用户裁决。
4. 全部能力拆解完成后，汇总为完整台账表草稿，随 features 批次预览一起展示确认，确认后落盘（`workflows/persist.md`）。

## 更新追加规范

后续需求变化都**追加新行，不覆盖已有行**：

| 场景 | 登记方式 |
| --- | --- |
| 全新需求 | 追加一行，六列齐全 |
| 已有需求范围/目标变化 | 追加一行，需求内容注明"修改自 REQ-00X：变更要点" |
| 需求被放弃 | 追加一行，需求内容注明"废弃 REQ-00X：原因/替代方案" |

每次追加后更新 frontmatter 的 `lastUpdated` 为当前日期。拆用户故事前的"台账新鲜度检查"以 `lastUpdated` 为据（`references/story-map/instruction.md`）。

## 追溯与引用

- 落盘后在 `refs.json` 注册 `requirement-ledger` 节点；edges 记录台账与所属能力的关系（`需求台账 ──references──▶ Feature`，逐条目的归属经"所属Feature"列表达），见 `references/shared/traceability-model.md`。
- User Story 通过 frontmatter `refs: [{id: "<条目ID>", relation: "addresses"}]` 关联具体条目（机器链）；一条条目可被多条 Story `addresses` 落实。
- Story 正文引用使用文件链接 + 条目ID：`[[<产品简称>-需求台账|<条目ID>]]`。禁止裸条目 ID 链接（`[[网资-REQ-001]]`）——条目不是文件，会断链。
