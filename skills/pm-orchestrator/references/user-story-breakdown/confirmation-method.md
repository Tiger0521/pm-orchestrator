# 提问与确认方法

本文件在 `mode=draft` 需要与用户确认拆解决策时读取。通用交互协议（每轮一题、选项格式、兜底）见 `references/orchestrator/output-format.md`，本文件定义 user-story-breakdown 阶段的确认方法。

用户选定候选 Story 后的决策问题、推荐答案、依赖顺序、共同理解门禁与 JSON 状态更新一律以 `grilling-protocol.md` 为准；本文件只处理候选选择前和共同理解后各阶段产出的展示与确认，不重复盘问规则。

## 理解回执

每次用户回答后、下一轮确认或提问前，必须先用 2-5 行反馈当前理解：

```text
已确认：
- 角色：VIP 会员、系统管理员
- 主干 Story：创建配置、查看配置列表、编辑配置
- 异常场景：已覆盖权限不足、名称重复、连接超时
待确认：是否需要补充“批量导入配置”的体验型 Story
```

回执不是第二个问题，不得夹带新的追问。回执的目的是让用户在下一轮确认前有机会纠偏。如果理解有误，用户先纠偏，再继续。

## 确认流程

9 步工作流中，第 2 步、第 3a 步、每条已选 Story 的第 3b 步，以及第 4、5、6、7 步需要用户确认。第 3a 步用于选择讨论范围；第 3b 至第 7 步的决策先完成 `grilling-protocol.md` 的共同理解门禁，再在这里确认相应产出。确认不是简单问“对吗？”，而是：

1. 先展示结构化产出（角色-规则-流程摘要 / Story 草稿清单 / 异常分支清单 / 完整 Story 落盘预览 / 优先级和估算清单 / 溯源矩阵），每条用加粗关键词领条。
2. 再给出理解回执（已确认了什么、待确认什么）。
3. 最后提出一个聚焦问题（选择题或确认题），遵守每轮一个问题原则。

确认问题示例：

| 步骤 | 确认问题 |
| ---- | -------- |
| 第 2 步（角色规则） | “以上角色和规则覆盖了本次拆解的全部用户场景，还是需要补充？” |
| 第 3a 步（候选总表） | “以上候选分别由哪个能力拆出已标明。请选本轮值得深入讨论的一个或多个标签（如 A、C、F）；哪些暂不讨论？” |
| 第 3b 步（已选 Story） | “盘问回执中的事实、决策、依赖和强制跳过项是否准确，且我们已达成共同理解？” |
| 第 4 步（异常分支） | “异常决策回执是否准确，且我们已达成共同理解，可以生成异常清单？” |
| 第 5 步（GWT） | “验收决策回执是否准确，且我们已达成共同理解，可以生成 GWT？” |
| 第 6 步（优先级） | “排序与估算决策回执是否准确，且我们已达成共同理解，可以生成建议清单？” |
| 第 7 步（溯源矩阵） | “溯源与覆盖决策回执是否准确，且我们已达成共同理解，可以生成矩阵草稿？” |

不得问“对吗？”：确认问题必须有具体指向，例如“需要调整或合并哪些？”“有没有遗漏？”“标准是否过严或过松？”。不要问“对吗？”“可以吗？”“有没有问题？”这种无指向的确认。

确认后按 `grilling-protocol.md` 更新 Story JSON 中相应决策组的 `shared_understanding` 和 `decision_tree` 状态。用户提出修改时，受影响节点保持 `pending`，下一轮只问其依赖已满足的直接缺口。

## 阶段性确认优先级

只有盘问协议已收敛相应决策组、同一轮仍有多个阶段性确认项时，按以下优先级选择只问一个：

1. 影响后续所有拆解的基础决策（角色、范围）。
2. 影响 Story 数量和颗粒度的拆分方案。
3. 影响验收标准的异常场景。
4. 优先级和估算。
5. 溯源矩阵覆盖度。

## 范围漂移防护

如果用户在确认过程中提出新的角色、新的异常场景或新的 Feature 范围，必须判断是否属于当前拆解范围：

- 新角色在已有 Feature 的用户角色字段中：纳入，补充对应 Story。
- 新异常场景在已有 Feature 的业务规则中：纳入，补充对应 AC。
- 新角色或新场景不在已有 Feature 中：写入当前 Story JSON 的冲突/范围记录，标记为“超出当前拆解范围，需回到需求分析阶段补充 Feature”，返回主调度器；本次不展开，也不得在 `draft` 模式写入 `tracking-log.md`。
