# 需求拆解执行流程

本文件在 `mode=draft` 执行 user-story-breakdown 时读取，定义 9 步工作流、上游质量门和项目类型自适应规则。

## 总体流程

当前工作流分为 9 步，按两段执行。第一段读取上游、梳理角色规则并拆分主干 Story；第二段补充异常分支、编写 GWT 并生成溯源矩阵。

第 2 步、第 3a 步、每条已选 Story 的第 3b 步，以及第 4、5、6、7 步需要用户确认。确认方法见 `confirmation-method.md`。

## 第一段：读取上游 + 主干拆分

### 第 1 步：读取上游文档

- 读取 `refs.json`，筛选 Epic 和 Feature 节点。
- 读取所有 Feature 和 Epic 文档的 frontmatter 和正文，尤其关注业务流程、业务规则、用户角色、能力描述、能力目标字段。
- 检查上游质量门（见下方“上游质量门”），不通过时返回 `needs-input`。

### 第 2 步：梳理角色和规则

- 从 Epic 用户角色表和 Feature 用户角色字段中汇总所有角色。
- 从 Feature 业务规则字段中汇总所有业务规则。
- 从 Feature 业务流程字段中汇总所有业务流程步骤。
- 输出“角色-规则-流程”摘要回执，按确认流程向用户确认（先展示摘要，再给理解回执，最后提聚焦问题）。

### 第 3 步：先自主拆解候选，再由用户选择并逐条完善主干 Story

这是本阶段的核心操作。候选生成与范围选择先读取 `core-mechanisms.md`、`writing-paradigm/user-story-writing.md` 和 `confirmation-method.md`；用户选定候选后才读取 `grilling-protocol.md`。不得跳过候选总表而直接要求用户从空白开始编写 Story。

1. **自主生成候选**：基于已读取的 Epic 用户角色、Feature 的能力目标、业务流程和业务规则，先由 AI 为每个 Feature 拆出主干 Story 候选。每个候选必须明确来源 Epic、来源 Feature、来源能力、角色、用户目标、业务价值和拟覆盖的主流程步骤；先做 INVEST 与颗粒度自检。此时不编写 GWT，也不把候选当作已确认的正式 Story。
2. **展示候选总表**：按 `core-mechanisms.md` 的“主干 Story 候选总表”格式输出概述表。表格必须写清每条候选由哪个 Feature/能力拆出，不能只给 Story 名称或按页面/技术模块分组；候选标签使用大写字母。
3. **让用户初步选择讨论范围**：展示总表和理解回执后，只问一个聚焦问题：请用户选择本轮值得深入讨论的一个或多个候选标签。用户可回复多个大写字母（如 `A、C、F`）；仍遵守“补充描述”和“强制跳过”兜底选项。未选候选保留在总表中，不得擅自当作已确认或删除。
4. **创建状态并盘问已选 Story**：为每条已选候选创建或恢复 `story-<nnn>.json`，写入来源信息后按 `grilling-protocol.md` 盘问。先收敛共同依赖，再逐条 Story 沿决策树解决价值、角色、流程、规则和依赖；异常、验收、优先级与溯源节点在第 4 至第 7 步按同一协议继续收敛。每轮只问一个决策并立即更新 JSON。不得在共同理解前输出完整 Story、GWT 或落盘预览。
5. **共同理解后生成草稿**：仅在适用节点都由用户确认或被用户明确强制跳过、且用户确认共同理解后，才基于 JSON 的最终润色值生成对应的完整 Story、异常清单、GWT、优先级/估算清单或矩阵草稿。Story/AC 的确认状态和共同理解状态均写回 JSON。
6. **进入下一步的条件**：所有选中 Story 的相关决策组均已通过共同理解门禁后，才进入最终完整预览与落盘确认。未选候选不生成 GWT、不进入落盘，也不计入本轮确认范围。

## 第二段：异常分支 + GWT + 溯源矩阵

### 第 4 步：枚举异常分支

- 先依据上游业务规则和已确认事实判断哪些异常类型相关；可确认的事实不向用户提问。
- 对仍需用户裁决的异常、兜底或拆分边界，按 `grilling-protocol.md` 一项一问；用户确认共同理解后才生成异常清单。
- 异常场景作为独立 AC 或独立 Story（视 `core-mechanisms.md` 的颗粒度判断决定）。不相关或被强制跳过的异常必须在 Story JSON 中记录理由。

### 第 5 步：编写 GWT 验收标准

- 对验收口径中仍未决定的成功、失败和边界结果，按 `grilling-protocol.md` 逐项盘问；共同理解确认后写入 JSON 的 AC 字段。
- 为每条 Story 编写 3-8 条 GWT，覆盖正常路径、相关异常路径和边界场景，并按 `core-mechanisms.md` 检查格式。
- 只有完整 Story/GWT、优先级和溯源决策组都已确认后，才输出完整落盘预览并按确认流程请求落盘确认。

### 第 6 步：优先级排序与 Story Points 估算

- 先以 Feature 优先级、依赖和已确认业务价值形成推荐；优先级排序、Story Points 和拆分/合并裁决仍按 `grilling-protocol.md` 逐项由用户决定。
- 共同理解确认后，将优先级和 Story Points 建议写入 JSON；估算超过 13 的 Story 必须按 `core-mechanisms.md` 拆分。

### 第 7 步：生成溯源矩阵

- 先从 JSON 和上游 Feature 计算 Story 与 Feature 的追溯关系、覆盖度及 P0 缺口。
- 覆盖范围、重复覆盖或未覆盖的处理仍需用户决策时，按 `grilling-protocol.md` 逐项盘问；共同理解确认后才输出矩阵草稿并按确认流程请求落盘确认。

### 第 8 步：用户确认

- 用户确认 Story 拆解方案、优先级、Story Points 和 GWT 验收标准。
- 用户确认溯源矩阵覆盖度。
- 用户确认前，不进入落盘。

### 第 9 步：落盘

- 当 `mode=persist` 且用户已确认时，读取 `persist-guide.md` 执行落盘流程。
- 不用 AI 逐行 Write：Story 和溯源矩阵的 Markdown 文件由脚本渲染写入，AI 只负责准备结构化数据。

## 上游质量门

拆解前检查上游文档质量：

- Feature 的业务流程字段非空，含关键步骤和触发条件。
- Feature 的业务规则字段非空，含异常处理。
- Epic 的用户角色字段非空，含角色诉求。
- 如果上游文档存在字段缺失或内容空洞，向主调度器返回 `needs-input`，附注缺失字段清单。
- 检查上游 Feature 的 `status` 是否为 `approved` 或 `review`；若有 Feature 仍为 `draft`，向主调度器报告 `needs-input`。

## 规模自适应

项目类型在需求分析 intake 中收敛，写入 `progress.json` 的 `projectType` 字段。需求拆解阶段读取该字段决定流程深度：

| 环节 | 全新项目 (`new`) | 迭代项目 (`iteration`) | 重构项目 (`refactor`) |
| ---- | -------- | -------- | -------- |
| 上游读取 | 读取全部 Feature + Epic | 读取新增 Feature + 关联 Epic | 读取全部 Feature + Epic |
| 角色梳理 | 完整列出所有角色 | 聚焦新增能力涉及的角色 | 聚焦受影响角色和权限变化 |
| Story 拆分 | 完整拆分全部 Feature | 聚焦新增 Feature 的 Story 拆分 | 只产出非功能性需求的 Story（性能、安全、兼容性等） |
| 异常枚举 | 完整枚举 | 聚焦新增能力的异常场景 | 聚焦重构引入的新异常场景 |
| 覆盖度检查 | 全部 Feature 覆盖 | 新增 Feature 覆盖 | 已有 Feature 覆盖 |

路由不是机械省略。若拆解过程中暴露上游 Feature 信息不足，返回主调度器要求补问或回退。
