# 能力分类规则与方法

## 用途

本文件定义能力文档（Feature）的智能分类组织规则。在 `features` 批次的 `draft` 阶段，AI 根据能力名称和描述自动判断分类，在 `persist` 前展示分类建议让用户确认；落盘时按分类创建文件夹、添加 `category` 字段并建立同类能力的引用关系。

**重要说明**：分类是文件夹组织方式，**每个能力文档保持独立**，不合并内容。所有能力文档仍然保持独立的 `.md` 文件，只是按类别放到不同的文件夹中。

## 分类原则

### 1. AI 自主判断，不限定固定规则

能力分类不预设固定分类体系。AI 应根据产品特点和能力实质，自主提出合理的分类方案。常见分类维度参考：

| 分类维度 | 示例 | 适用场景 |
| --- | --- | --- |
| **数据管理类** | 数据录入、数据导入、数据查询、数据导出、数据同步 | 以数据操作为核心的能力 |
| **服务输出类** | 报告生成、单据打印、消息推送、API 接口 | 向用户或外部系统输出信息或服务的能力 |
| **质量反馈类** | 数据校验、异常检测、质量评分、审核流程 | 保障质量、识别问题、提供反馈的能力 |
| **运营支撑类** | 权限管理、配置管理、日志审计、统计分析 | 支持系统运营和管理的能力 |
| **业务流程类** | 订单处理、审批流程、工单流转、状态机管理 | 实现特定业务流程的能力 |
| **交互体验类** | 可视化展示、批量操作、快捷入口、个性化设置 | 提升用户交互体验的能力 |

AI 可根据产品领域提出新的分类维度，例如：
- 教育产品：内容类、互动类、评估类、激励类
- 金融产品：交易类、风控类、清算类、报表类
- 物流产品：调度类、跟踪类、结算类、客服类

### 2. 分类粒度

分类粒度应根据能力的实际特征和关联性判断，不设固定数量限制。

**判断原则**：
- **合理分类**：同一分类内的能力应具有明确的共同特征和相似的业务职责
- **避免过细**：若某分类只有很少能力且与其他分类关联性强，考虑是否可以合并
- **避免过粗**：若某分类包含的能力过多且内部差异明显，考虑是否可以进一步细分

**关键**：分类的目的是帮助理解能力之间的关系，不是机械地平均分配数量。具体内容具体分析。

**注意**：分类粒度指的是每个文件夹包含的文档数量，不是合并能力内容。

### 3. 分类命名与文件夹结构

- **文件夹命名格式**：`{产品简称}-{分类名}能力/`
- **文件命名格式**：`{产品简称}-{分类名}能力-{能力简称}-能力文档.md`
- **示例结构**：
  ```
  {产品简称}/
  ├── {产品简称}-{分类名1}能力/
  │   ├── {能力简称A}/
  │   │   ├── {产品简称}-{分类名1}能力-{能力简称A}-能力文档.md
  │   │   └── stories/
  │   │       ├── story-001.md
  │   │       └── story-002.md
  │   └── {能力简称B}/
  │       ├── {产品简称}-{分类名1}能力-{能力简称B}-能力文档.md
  │       └── stories/
  │           └── story-003.md
  ├── {产品简称}-{分类名2}能力/
  │   └── {能力简称C}/
  │       ├── {产品简称}-{分类名2}能力-{能力简称C}-能力文档.md
  │       └── stories/
  │           └── story-004.md
  ```
- **命名规则**：
  - 产品简称从 `progress.json` 的 `productShortName` 字段读取（在 intake 阶段已确认）
  - 分类名简洁明确（2-5 个字），统一使用"类"字标识
  - **文件夹结构**：
    ```
    {产品简称}-{分类名}能力/
    ├── {能力简称}/                                       # 能力子文件夹
    │   ├── {产品简称}-{分类名}能力-{能力简称}-能力文档.md  # 能力文档
    │   └── stories/                   # Story 文件夹（如果有）
    │       └── story-xxx.md
    ```
  - **能力子文件夹命名**：使用能力简称（从能力名称中提取，去掉产品名前缀和"能力"后缀）
  - **能力文档命名**：`{产品简称}-{分类名}能力-{能力简称}-能力文档.md`
  - **Story 文件夹**：统一命名为 `stories/`，存放该能力的所有 Story 文档
  - **每个能力文档保持独立**，按分类移动到对应子文件夹并重命名

## 分类判断流程

### 阶段 1：能力清单确认后

在 `artifactScope=features` 且能力清单已确认时（第 7 步完成后、第 8 步详细字段追问前），执行分类判断：

**输入**：能力清单（能力名称 + 简要任务描述）

此时尚未进行详细字段追问，只有从第 7 步获得的基本信息：
- 能力名称
- 每个能力解决哪类用户任务（简要描述）

**步骤**：

1. **提取分类依据**：
   - 能力名称
   - 任务类型（用户在第 7 步提供的"解决哪类用户任务"）
   
   **注意**：此时尚未追问详细字段（能力描述、能力目标、业务场景等），只能基于能力名称和任务类型判断分类。这是有意的设计——用轻量信息先确定分类框架，再用分类框架引导后续详细字段的追问。

2. **AI 自主判断分类**：
   - 根据能力的核心职责和业务特征判断所属分类
   - 提出完整的分类方案（包含分类名称、判断依据）
   - 允许为本产品创造新的分类维度

3. **生成分类建议预览**：
   ```markdown
   ### 能力分类建议

   根据 {n} 个能力的职责和特征，建议按以下方式分类：

   #### {产品简称}-{分类名1}能力（{数量1}个）
   - **{能力名称}**：{分类依据}
   - **{能力名称}**：{分类依据}
   - ...

   #### {产品简称}-{分类名2}能力（{数量2}个）
   - **{能力名称}**：{分类依据}
   - **{能力名称}**：{分类依据}
   - ...

   **分类原则说明**：
   - {分类名1}：{该分类的判断标准和包含能力的共同特征}
   - {分类名2}：{该分类的判断标准和包含能力的共同特征}
   - ...

   以上分类是否合理？如需调整，请说明。
   ```

4. **等待用户确认**：
   - 用户确认：记录分类方案，进入 `draft-ready`
   - 用户调整：根据用户意见修改分类，重新展示，直到确认
   - 在 Feature 字段 JSON 中临时记录 `_category` 字段（不渲染到最终 Markdown）

### 阶段 2：persist 执行时应用分类

在 `mode=persist`、`artifactScope=features` 时，根据已确认的分类方案落盘：

1. **按分类创建文件夹**：
   - 在产品库目标目录下创建 `{产品简称}-{分类名}能力/` 子文件夹
   - 每个分类对应一个文件夹

2. **更新文件名并移动**：
   - 将能力文档按分类重命名为：`{产品简称}-{分类名}能力-{能力简称}-能力文档.md`
   - 移动到对应的分类文件夹中
   - 能力简称从能力名称字段提取（去掉产品名前缀和"能力"后缀）

3. **更新 frontmatter**：
   - 在 Feature 的 frontmatter 中添加 `category: "{分类名}能力"` 字段
   - 更新文档内的文件 ID 以匹配新文件名

4. **添加同类引用**：
   - 在"## 能力描述"章节的内容之后、"## 能力目标"章节标题之前插入同类能力引用
   - 格式：
     ```markdown
     
     **同类能力**：
     - [[文件名1]]
     - [[文件名2]]
     ```
   - 使用简洁的 Obsidian 链接格式：`[[文件名]]`（文件名不含 .md 后缀）
   - 文件名示例：`产品A-数据管理类能力-地址查询-能力文档`
   - 排除当前文档自身
   - 按文件名字母顺序排列

## 分类修正规则

若用户对 AI 提出的分类不满意，应支持以下调整：

| 用户意图 | 操作 |
| --- | --- |
| 合并两个分类文件夹 | 将分类 B 文件夹中的能力文档移到分类 A 文件夹，删除分类 B 文件夹 |
| 拆分一个分类文件夹 | 将某个分类文件夹中的部分能力文档按新标准分到新建的文件夹 |
| 重命名分类文件夹 | 修改文件夹名称和其中文档的文件名，保持能力文档的业务内容不变 |
| 调整单个能力文档归属 | 将某个能力文档从一个分类文件夹移到另一个分类文件夹，并重命名 |
| 创建新分类文件夹 | 新增分类文件夹，从现有分类文件夹中移入相关能力文档 |

调整后重新生成分类建议预览，直到用户确认。

**关键原则**：调整的是文件夹组织结构和文档归属，不修改能力文档的业务内容。

## 质量检查点

在返回 `draft-ready` 前，必须通过以下检查：

- [ ] 每个 Feature 都有明确的分类归属
- [ ] 分类命名符合 `{产品简称}-{分类名}能力` 格式
- [ ] 每个分类包含至少 2 个能力（单能力分类需要用户明确确认）
- [ ] 分类依据清晰，能够解释为什么这些能力归为一类
- [ ] 用户已明确确认分类方案

## 与其他流程的关系

- **不影响字段 JSON 结构**：`_category` 是临时字段，不进入 `render-doc.sh` 的渲染流程
- **只在 features 批次生效**：`requirement-epic` 批次不涉及能力分类
- **不修改模板**：分类信息通过 frontmatter 和章节内容体现，不新增模板字段
- **兼容已有产品库**：若产品库已有能力文档但无分类，可通过 `mode=fix-category` 修补

## 边界说明

- 分类判断不依赖用户显式输入"请分类"，而是 `features` 批次的标准步骤
- 分类方案存储在 `phase-summary.md` 的 `feature-categories` 字段中，供 `persist` 读取
- `fix-category` 模式是独立工作流，不与正常 `draft`/`persist` 流程混合
