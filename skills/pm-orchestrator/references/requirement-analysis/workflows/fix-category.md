# 能力分类修补工作流

**前置条件**：主调度器以 `mode=fix-category` 调用，并传入 `productLibraryPath`（待修补的产品库目录路径）。

**独立模式说明**：本工作流完全独立于需求分析流程，不依赖过程项目状态、不需要 `projectPath`、`workflow.state`、`artifactScope` 等字段，不读取 `productArchitectureDesignPath` 或其他产品库上下文。它只操作用户指定的产品库目录，执行纯粹的文件重组和元数据更新。

**核心任务**：对已有产品库中的能力文档按类别重新组织文件夹结构。

**关键原则 - 分类≠合并**：
- **每个能力文档保持独立的 .md 文件**，不合并、不删除任何能力文档内容
- 分类只是文件夹组织方式：同一分类的文档放到同一文件夹下，仅此而已
- 操作内容：移动文件到分类文件夹、重命名文件、更新 frontmatter、添加引用链接
- **禁止操作**：不得将多个能力的内容写入同一个文件、不得删除任何能力文档

**按需读取**：`../guides/capability-classification.md`（只读取分类判断规则，不读取与需求分析流程相关的其他 guides）。

**允许操作**：读取产品库能力文档、创建分类文件夹、移动文件、更新 frontmatter 和章节引用。

**终点**：用户确认分类方案后返回 `fix-category-completed`；路径不存在或无能力文档时返回 `blocked`。

## 用途

修补已有产品库中缺少分类的能力文档。执行能力分类判断、文件夹重组和引用更新，但不修改能力的业务内容字段。

## 执行步骤

**关键原则**：fix-category 是一个**完整的执行流程**，不是仅提供建议。必须按顺序完成以下所有步骤：

1. 扫描并读取能力文档
2. AI 判断分类并展示建议 → **等待用户确认**
3. 展示文件重组预览 → **等待用户确认**
4. **执行实际文件操作**（创建文件夹、重命名文件、更新内容、删除原文件）
5. 生成操作报告并返回 `fix-category-completed`

**禁止行为**：
- ❌ 只展示分类建议就结束
- ❌ 不等用户确认就跳过步骤
- ❌ 展示预览后询问"是否需要写回文档"（必须直接执行文件操作）
- ❌ 在任何步骤提前返回 `fix-category-completed`（必须完成所有文件操作后才能返回）

### 第 1 步：扫描并读取能力文档

1. **校验输入路径**：
   - 确认 `productLibraryPath` 存在且可读
   - 确认路径指向产品库根目录（包含产品简称文件夹或能力文档）
   - 路径不存在或不可读时返回 `blocked`

2. **扫描能力文档**：
   ```bash
   find "<productLibraryPath>" -type f -name "*.md" | grep -E "(feature-|能力)" 
   ```
   - 识别文件名包含 `feature-` 或"能力"的 Markdown 文件
   - 至少找到 2 个能力文档才继续；否则返回 `blocked` 并提示"未找到足够的能力文档"

3. **读取文档内容**：
   - 读取每个能力文档的 frontmatter（提取 `id`、`title`、`category`）
   - 读取"能力名称"、"能力描述"、"能力目标"、"业务场景"章节
   - 记录当前文件路径和所在文件夹

4. **检查已有分类**：
   - 统计有 `category` 字段的文档数量
   - 统计当前文件夹分布情况
   - 向用户展示当前结构概览：
     ```markdown
     ### 产品库当前结构

     共找到 {n} 个能力文档：
     - 已有分类：{m} 个（分类字段存在）
     - 未分类：{k} 个（缺少分类字段）

     当前文件夹分布：
     - 根目录：{x} 个文档
     - {文件夹名1}：{y} 个文档
     - {文件夹名2}：{z} 个文档
     ```

### 第 2 步：AI 重新判断分类

1. **应用分类规则**：
   - 读取 `../guides/capability-classification.md`
   - 按其中的"分类判断流程"，对全部能力文档进行分类判断
   - 忽略现有的 `category` 字段和文件夹结构，从零开始判断

2. **生成分类建议**：
   - 提出完整的分类方案（分类名称、每个分类包含的能力）
   - 对每个能力给出分类依据（为什么归入该类）
   - 检查分类粒度（每类 3-8 个能力为宜）

3. **展示分类建议**：
   ```markdown
   ### 建议的新分类方案

   根据 {n} 个能力的职责和特征，建议重新分类如下：

   #### {产品简称}-{分类名1}能力（{数量1}个）
   - **{能力名称}** (`{原文件名}`)：{分类依据}
   - **{能力名称}** (`{原文件名}`)：{分类依据}
   - ...

   #### {产品简称}-{分类名2}能力（{数量2}个）
   - **{能力名称}** (`{原文件名}`)：{分类依据}
   - **{能力名称}** (`{原文件名}`)：{分类依据}
   - ...

   **分类原则说明**：
   - {分类名1}：{该分类的判断标准和包含能力的共同特征}
   - {分类名2}：{该分类的判断标准和包含能力的共同特征}
   - ...

   **与当前结构的差异**：
   - {差异点1：新增/删除/重命名/移动的说明}
   - {差异点2：新增/删除/重命名/移动的说明}
   - ...

   以上分类是否合理？如需调整，请说明。
   ```

4. **等待用户确认**：
   - **必须等待用户明确回复**（如"确认"、"可以"、"执行"等）
   - 用户调整：根据用户意见修改分类，重新展示步骤 3，直到确认
   - **禁止行为**：不得在用户确认前就结束对话或询问"是否需要写回文档"
   - **确认后必须立即进入第 3 步**展示重组预览，不得停止

### 第 3 步：展示重组预览

用户确认分类方案后，**在对话中**生成文件重组预览（不写入文件）：

```markdown
### 文件重组预览

将执行以下操作：

**重要说明**：这是文件夹重组，每个能力文档保持独立，不合并内容。

#### 创建分类文件夹
- `{产品简称}-{分类名1}能力/`
- `{产品简称}-{分类名2}能力/`
- `{产品简称}-{分类名3}能力/`
- ...

#### 移动能力文档（文件保持独立，只改变所在文件夹）
- `{原文件名}.md` → 重命名为 `{产品简称}-{分类名}能力-{能力简称}-能力文档.md` → `{产品简称}-{分类名}能力/`
- `{原文件名}.md` → 重命名为 `{产品简称}-{分类名}能力-{能力简称}-能力文档.md` → `{产品简称}-{分类名}能力/`
- ...

**文件名规则**：`{产品简称}-{分类名}能力-{能力简称}-能力文档.md`

#### 更新文档元数据（不修改业务内容）
每个能力文档将更新：
1. 文件名按格式重命名：`{产品简称}-{分类名}能力-{能力简称}-能力文档.md`
2. frontmatter 添加 `category: "{分类名}能力"` 字段
3. frontmatter 更新文档 ID 以匹配新文件名
4. "需求背景"章节末尾添加同类能力引用（使用新的文件 ID）

#### 清理旧结构
- 删除空文件夹（若有）
- **不删除、不合并任何能力文档**

确认执行？（yes/no）
```

**第 3 步执行要点**：
- **必须等待用户明确回复**（如"yes"、"确认"、"执行"等）
- 用户回复 no 或取消：返回 `needs-input`，不执行文件操作
- **用户确认后，必须立即进入第 4 步执行实际文件操作**
- **禁止行为**：不得在展示预览后就结束对话或询问其他问题

### 第 4 步：执行重组

**前置条件**：用户已在第 3 步明确确认执行

用户确认后，**必须**按以下顺序执行：

1. **创建文件夹结构**：
   对每个能力：
   
   a. **创建能力子文件夹**：
      ```bash
      mkdir -p "<productLibraryPath>/{产品简称}-{分类名}能力/{能力简称}"
      ```
   
   b. **创建 stories 子文件夹**（如果该能力有 Story 文档）：
      ```bash
      mkdir -p "<productLibraryPath>/{产品简称}-{分类名}能力/{能力简称}/stories"
      ```
   
   - 能力简称从能力名称字段提取（去掉产品名前缀和"能力"后缀）
   - 若文件夹已存在，跳过创建

2. **逐个文档处理**：
   **重要**：必须逐个文档独立处理，每个能力文档生成一个独立的新文件。
   
   对每个能力文档（循环处理，一次处理一个）：
   
   a. **读取原文件内容**
      - 读取当前能力文档的完整内容
      - 只处理这一个文档，不涉及其他文档
   
   b. **生成新文件路径**：
      - 能力子文件夹：`{产品简称}-{分类名}能力/{能力简称}/`
      - 能力文档名：`{能力简称}-能力文档.md`
      - 完整路径示例：`产品A-数据管理类能力/地址录入/地址录入-能力文档.md`
      - 能力简称从能力名称字段提取（去掉产品名前缀和"能力"后缀）
   
   c. **更新 frontmatter**：
      - 添加或更新 `category: "{分类名}能力"` 字段
      - 更新 `id` 字段以匹配新文件名（去掉 `.md` 后缀）
      - 保持其他 frontmatter 字段不变
   
   d. **添加同类能力引用**：
      - 在"## 能力描述"章节的内容之后、"## 能力目标"章节标题之前插入同类引用
      - 插入位置示例：
        ```
        ## 能力描述
        
        [能力描述的内容...]
        
        **同类能力**：        ← 插入在这里
        - [[产品A-数据管理类能力-地址查询-能力文档]]
        - [[产品A-数据管理类能力-地址导出-能力文档]]
        
        ## 能力目标           ← 下一个章节
        ```
      - 格式：
        ```markdown
        
        **同类能力**：
        - [[文件名1]]
        - [[文件名2]]
        ```
      - 使用简洁的 Obsidian 链接格式：`[[文件名]]`（文件名不含 .md 后缀）
      - 文件名就是能力文档的完整文件名（去掉 .md），如 `产品A-数据管理类能力-地址查询-能力文档`
      - 排除当前文档自身
      - 按文件名字母顺序排列
   
   e. **移动文件到新结构**：
      ```bash
      # 能力文档路径
      capability_folder="<productLibraryPath>/{产品简称}-{分类名}能力/{能力简称}"
      new_filename="{能力简称}-能力文档.md"
      target="$capability_folder/$new_filename"
      
      # 写入更新后的能力文档内容（使用 Write 工具）
      # ⚠️ 关键：只写入当前这一个能力文档的内容，不包含其他能力的内容
      
      # 删除原文件（如果路径或文件名不同）
      if [ "$original" != "$target" ]; then
        rm "$original"
      fi
      ```
   
   f. **移动 Story 文档**（如果存在）：
      ```bash
      # 查找对应的 Story 文件夹（可能是 feature-{nnn}/ 或其他命名）
      # 如果找到，将其中的 Story 文档移到 stories/ 子文件夹
      
      if [ -d "原Story文件夹路径" ]; then
        mv "原Story文件夹路径"/*.md "$capability_folder/stories/"
        rmdir "原Story文件夹路径"  # 删除空的原 Story 文件夹
      fi
      ```
   
   f. **验证文件独立性**：
      - 确认新文件只包含当前能力的内容
      - 确认文件数量：处理 N 个能力文档，必须生成 N 个独立的新文件
      - 若发现文件数量减少，立即停止并报错

3. **清理空文件夹**：
   ```bash
   find "<productLibraryPath>" -type d -empty -delete
   ```

4. **生成操作报告**：
   **在对话中展示**完成报告（不写入文件）：
   ```markdown
   ### 分类修补完成

   已完成 {n} 个能力文档的分类修补：

   #### {产品简称}-{分类名1}能力（{数量1}个）
   - {产品简称}-{分类名1}能力-{能力简称1}-能力文档.md
   - {产品简称}-{分类名1}能力-{能力简称2}-能力文档.md
   - ...

   #### {产品简称}-{分类名2}能力（{数量2}个）
   - {产品简称}-{分类名2}能力-{能力简称3}-能力文档.md
   - {产品简称}-{分类名2}能力-{能力简称4}-能力文档.md
   - ...

   所有文档已按分类重命名、移动到分类文件夹，并更新 frontmatter 和同类引用。
   ```

### 第 5 步：返回状态

返回 `fix-category-completed`，并在调度回执中包含：
- `productLibraryPath`：已修补的产品库路径
- `categoriesCreated`：创建的分类文件夹列表
- `documentsUpdated`：更新的文档数量
- `summary`：操作摘要（用户可见）

## 安全规则

1. **只修改能力文档**：不修改需求卡片、Epic、设计文档等其他类型文档
2. **不修改业务内容**：只更新文件名、frontmatter 和章节引用，不改写能力描述、业务规则等字段
3. **重命名文件**：按格式 `{产品简称}-{分类名}能力-{能力简称}-能力文档.md` 重命名并移动到分类文件夹
4. **更新文档 ID**：frontmatter 的 `id` 字段必须与新文件名一致（去掉 `.md` 后缀）
5. **备份提示**：执行前提示用户"建议先备份产品库目录"
6. **原子操作**：若任一文档更新失败，报告错误并停止，不继续处理后续文档
7. **🔴 禁止合并**：
   - 严禁将多个能力的内容写入同一个文件
   - 处理 N 个能力文档，必须生成 N 个独立的 .md 文件
   - 每个能力文档只能包含该能力自身的内容，不得包含其他能力的字段或章节
   - 同类引用只添加 `[[文件名]]` 格式的链接，不复制其他能力的内容到当前文档
8. **🔴 禁止生成 README**：
   - 不得在分类文件夹下创建 README.md、说明文件或任何非能力文档的文件
   - 分类文件夹只包含能力文档 .md 文件
9. **🔴 禁止生成方案文档**：
   - 不得生成"归类整理方案.md"、"分类方案.md"等额外说明文件
   - 分类建议、操作报告等信息只在对话中展示，不落盘成文件
   - 只修改能力文档本身，不创建任何辅助文档

## 错误处理

| 错误情况 | 返回状态 | 用户提示 |
| --- | --- | --- |
| `productLibraryPath` 不存在 | `blocked` | 产品库路径不存在，请检查路径是否正确 |
| 找不到能力文档 | `blocked` | 该目录下未找到能力文档（*.md） |
| 能力文档少于 2 个 | `blocked` | 能力文档数量不足（少于 2 个），无需分类 |
| 文件读取失败 | `blocked` | 无法读取文档 {file_path}，请检查权限 |
| 文件写入失败 | `blocked` | 无法写入文档 {file_path}，请检查权限和磁盘空间 |
| 用户取消操作 | `needs-input` | 已取消分类修补操作 |

## 与其他工作流的关系

- `fix-category` 是独立模式，不与 `draft`/`persist` 流程混合
- 不读取或修改过程项目文件（`docs/_extracted/`、`progress.json` 等）
- 只操作产品库目标目录，不涉及 `projectPath`
- 执行完成后不推进 `workflow.state`
- 主调度器在用户明确要求"修补已有产品库分类"时调用
