# 旅程叙事线提取指南

## 1. 从设计文档提取全局旅程

### 1.1 提取来源

设计文档（`productArchitectureDesignPath`）通常包含以下可用于提取旅程的章节：

| 章节名（可能变体） | 提取内容 |
| --- | --- |
| 核心场景 / 核心业务场景 | 用户完成业务目标的主要流程步骤 |
| 用户角色 / 目标用户 | 参与旅程的角色 |
| 产品目标 / 业务目标 | 旅程的起点和终点 |
| 建设思路 / 建设方向 | 旅程阶段的宏观划分线索 |
| 范围边界 | 旅程的边界（哪些不在旅程内） |

### 1.2 提取方法

1. **定位核心场景**：在设计文档中找到"核心场景"或类似章节。如果不存在，从"产品目标"和"用户角色"推断。
2. **识别流程步骤**：核心场景中通常描述了用户从开始到完成目标的流程。识别其中的关键步骤。
3. **聚类为阶段**：将细粒度步骤聚类为 3-6 个宏观阶段。聚类原则：
   - 每个阶段有一个明确的用户目标。
   - 阶段之间有先后关系（前一个阶段的输出是后一个阶段的输入）。
   - 阶段名称简短（2-4 个字），使用动宾结构（如"建址""维址""用址"）。
4. **排序阶段**：按用户完成业务目标的时间顺序从左到右排列。
5. **撰写阶段描述**：为每个阶段写一句话描述，说明用户在该阶段要完成什么。

### 1.3 提取示例

设计文档核心场景摘录：
> 用户需要创建地址 -> 录入/导入地址信息 -> 校验和审核 -> 地址入库 -> 日常维护和状态管理 -> 业务系统查询使用 -> 质量问题发现和治理 -> 运营监控

提取结果：
- **建址**：用户创建地址实体，包括手工录入、批量导入、智能解析和审核核准
- **维址**：用户维护地址状态，包括属性修改、启用/停用/废弃和历史追溯
- **用址**：用户查询和使用地址，包括搜索、选址、详情查看和合规校验
- **治址**：用户治理地址质量，包括问题发现、重复合并、标准化和纠错反馈
- **运址**：用户监控和运营地址平台，包括看板、告警、统计和分析

## 2. 将能力映射到旅程阶段

### 2.1 映射来源

每个能力文档通常包含"业务场景"和"业务流程"字段，用于判断该能力服务于哪个旅程阶段。

### 2.2 映射方法

1. 读取能力文档的"业务场景"字段，理解该能力解决什么业务问题。
2. 读取能力文档的"业务流程"字段，理解该能力的操作流程。
3. 将能力的主要业务目标与旅程阶段的目标匹配：
   - 如果能力主要服务于创建地址 -> 映射到"建址"
   - 如果能力主要服务于维护地址 -> 映射到"维址"
   - 以此类推
4. 一个能力可能跨越多个阶段：
   - 如果能力的业务流程覆盖多个阶段（如"地址全生命周期管理"覆盖创建和维护），映射到多个阶段。
   - 在能力覆盖矩阵中标注"主要"和"辅助"。

### 2.3 映射决策表

| 能力的业务场景关键词 | 推荐旅程阶段 |
| --- | --- |
| 创建、录入、导入、审核、核准 | 建址 |
| 维护、修改、状态、启用、停用、废弃 | 维址 |
| 查询、搜索、选址、详情、API、校验 | 用址 |
| 质量、治理、合并、标准化、纠偏、纠错、反馈 | 治址 |
| 监控、运营、看板、告警、统计、分析 | 运址 |
| 变更、事件、推送、订阅、同步 | 维址（或独立"同步"阶段） |
| 迁移、区划、批量 | 维址（或独立"迁移"阶段） |

### 2.4 特殊情况处理

- **一个能力覆盖多个阶段**：在覆盖矩阵中标注"主要"和"辅助"。该能力的故事在总览矩阵中分别出现在对应阶段的列中。
- **一个阶段没有能力覆盖**：标记为"覆盖空白"，向用户确认是否需要新增能力或调整阶段划分。
- **能力无法映射到任何阶段**：向用户确认该能力的旅程归属，或考虑新增旅程阶段。

## 3. 能力内旅程节点提取

### 3.1 提取来源

能力文档的"业务流程"字段通常描述了该能力内的操作步骤。这些步骤就是能力级地图的横轴节点。

### 3.2 提取方法

1. 读取能力文档的"业务流程"字段。
2. 识别流程中的关键步骤（通常 3-8 个节点）。
3. 为每个节点命名（简短动宾短语）。
4. 按流程顺序从左到右排列。
5. 如果业务流程中有条件分支，标注分支条件但不创建新的列（分支故事放在同一列的不同行）。

### 3.3 提取示例

能力文档业务流程摘录：
> 地址创建流程：用户提交地址信息 -> 系统智能解析补全 -> 校验地址格式和查重 -> 审核人员审核 -> 核准入库（如有歧义则消歧）

提取结果：
- 补全/解析 -> 录入/导入 -> 校验查重 -> 审核 -> 核准消歧

## 4. 旅程确认问题模板

向用户确认旅程阶段时，使用以下格式：

```
基于设计文档的核心场景，我提取了以下用户旅程阶段：

| 序号 | 阶段名称 | 阶段描述 | 覆盖能力 |
| --- | --- | --- | --- |
| 1 | 建址 | ... | 地址创建与审核能力 |
| 2 | 维址 | ... | 地址维护能力、变更事件能力 |
| ... | ... | ... | ... |

这个旅程阶段划分是否合理？

A. 合理，继续构建地图
B. 需要调整阶段数量或名称（请说明）
补充描述：我自己填写
强制跳过：这个问题暂时不回答，记录为待验证并继续
```
